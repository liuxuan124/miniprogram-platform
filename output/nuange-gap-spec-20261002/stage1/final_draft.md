# 暖阁小程序功能补足开发说明

## 一、背景目标

### 1.1 项目背景

客户交付物为《暖阁 · 内容平台小程序原型》（prototypes-warm，共十四个板块、二十余个页面），产品定位为暖色系内容平台：图文长文、小红书式笔记瀑布流、星球社群与话题预测、付费专栏与虚拟商品。内容生产分两阶段：阶段一仅运营团队产出（署名收敛为主理人、编辑部、特约作者三类），阶段二开放 UGC。

### 1.2 现状结论

经对现有系统（miniapp / admin / backend）的逐项核查，现有能力对原型的覆盖率约为 85%–90%。底部五个 Tab 中，首页、发现、星球、商城四页已支持装修页绑定，「我的」为原生页并具备三套皮肤与模板库；资料试读五态、服务端裁切、虚拟商品交付、会员权益开关、星球打卡、话题预测、邀请海报、Agent 与知识库后台等能力均已存在。

### 1.3 文档目的

本文档面向项目开发组长，说明为完整交付该客户所需补足的功能缺口，按 P0（必补）、P1（补齐）、P2（增强）三级分层，逐项给出现状、需求、改动点与验收标准，并附交付顺序建议。文档只描述缺口与要求，不涉及对现有系统的既有能力重复建设。

## 二、缺口总览

### 2.1 缺口分级

| 级别 | 数量 | 含义 | 交付门槛 |

| P0 | 3 项 | 原型明确呈现、系统完全没有对应物 | 必须完成才能交付 |
| P1 | 4 项 | 系统有基础，形态或完整性不足 | 建议随首版交付 |
| P2 | 3 项 | 增强项，可用现有能力变通 | 可排入后续迭代 |

### 2.2 缺口清单

| 级别 | 缺口 | 一句话说明 |
|------|------|-----------|
| P0 | 评论盖楼 | 评论仅单层，无楼中楼回复 |
| P0 | 音频形态 | 无音频内容类型与音频卡片组件 |
| P0 | 笔记详情 | 无小红书式笔记专属详情页 |
| P1 | 海报模板 | 分享海报仅封面款，缺金句款与纯文字款 |

| P2 | 群码轮换 | 群二维码七天轮换需人工操作 |

## 三、P0 必补项

### 3.1 评论盖楼

**现状**：内容评论为单层结构。评论实体（ContentComment）无父级字段，小程序端接口仅支持平铺列表与新增评论，原型笔记详情与星球动态详情中的「评论盖楼」无法实现。

**需求**：评论支持二级回复。在任意评论下可发起回复，展示侧按楼中楼形态呈现（父评论下聚合回复列表，超量折叠展开）；回复计入评论总数；回复内容同样经过内容安全检查。

**改动点**：

| 层 | 改动 |
|----|------|
| 数据库 | 评论表新增 parent_id、reply_to_user_id 两列，走 schema_version 迁移 |
| 后端 | 评论列表接口按父级聚合返回树形结构；新增回复接口校验父评论存在性 |
| 小程序 | content-detail 评论区块改为楼中楼组件，支持点按回复、折叠展开 |
| 管理端 | 评论管理（如有）同步展示层级关系 |

**验收标准**：发布一条二级回复后，详情页以楼中楼展示且计数正确；删除父评论时回复按既定策略处理（级联隐藏或保留占位）；含违规词的回复被安全检查拦截。

### 3.2 音频形态

**现状**：内容类型覆盖长文、笔记、动态三类，无音频；装修组件有视频组件但无音频组件；原型内容列表六种排版中的「音频波形卡」无对应物。

**需求**：内容支持音频形态（音频文件或音频附件）。小程序端提供音频卡片：封面、标题、时长、播放进度与波形样式，可在列表混排中出现，详情页内嵌播放器，支持后台播放与进度记忆（可选）。

**改动点**：

| 层 | 改动 |
|----|------|
| 后端 | 内容或附件模型扩展音频类型，记录时长与封面 |
| 小程序 | 新增音频卡片组件（InnerAudioContext），注册进 DSL 渲染器 |
| 装修器 | 配置面板与预览渲染器同步支持音频卡 |
| 管理端 | 内容编辑器支持上传音频并读取时长 |

**验收标准**：上传一段音频并发布后，音频卡出现在内容列表并可正常播放、暂停、拖动进度；混入图文列表排版不塌。

### 3.3 笔记详情

**现状**：内容详情为通用页面（长文导向），无按内容类型分叉的笔记专属形态。

**需求**：小红书式笔记详情页，包含：顶部作者栏（头像、昵称、官方身份标识）；多图轮播（带页码指示）；正文与可点击的话题标签（进入话题聚合流）；关联商品带货卡（点击跳商品详情）；底部评论区（楼中楼，依赖 3.1）。

**改动点**：

| 层 | 改动 |
|----|------|
| 小程序 | 新增笔记专属详情页，或 content-detail 按内容类型分叉渲染 |
| 后端 | 内容多图字段与话题标签、关联商品字段的接口下发（多图与标签字段已存在，需确认下发完整性） |
| 数据源 | 笔记瀑布流卡片跳转目标指向笔记详情 |

**验收标准**：笔记类型内容进入专属详情，轮播、话题标签、带货卡齐全且可点击；长文类型仍走原详情，互不影响。

## 四、P1 补齐项

### 4.1 海报模板

**现状**：分享页已具备 canvas 海报生成能力，仅封面款一种模板；邀请码通过 scene 参数携带。

**需求**：按原型补齐金句款与纯文字款，共三款海报模板可切换；海报携带专属小程序码，scene 不超过 32 字符（存短 ID 再查表，不直接拼接用户 ID 与内容 ID）；支持保存相册与直接发送。

**验收标准**：三款模板均可生成且版式正确；生成的小程序码扫码进入对应内容并正确落库邀请关系。

### 4.2 支付幂等

**现状**：微信支付配置链路完整（含 iOS 虚拟支付合规策略），但支付回调幂等未见显式实现证据。

**需求**：同一商户订单号重复回调只开通一次权限；支付成功页以轮询查单兜底「已扣款未开通」情形；提供定时补偿查询任务，对长时间未开通的已支付订单自动补开通或告警。

**验收标准**：模拟重复回调不产生重复开通；支付后断网重进能自动查到已开通状态；补偿任务可手动触发并输出处理清单。

### 4.3 失败三态

**现状**：支付失败为单一提示，未区分情形。

**需求**：支付失败区分三种情形并给出对应引导——未支付（引导重新支付）、已扣款未开通（引导查单补开通，依赖 4.2）、重复支付（提示已开通并引导查看订单）。三态建议做成公共组件。

**验收标准**：三种情形分别有独立文案与入口，客服侧可通过订单状态直接判断归属。

### 4.4 无网络态

**现状**：已有骨架屏与空列表组件，无网络异常态。

**需求**：新增公共无网络组件，监听网络状态变化，列表页与详情页统一接入，恢复网络后自动重载。

**验收标准**：断网进入任一主页面显示无网络态，恢复后自动刷新，不出现半加载残留。

## 五、P2 增强项

### 5.1 话题推演

**现状**：星球话题预测为配置下发（后台配置文案与百分比），组件已带「AI 推演」标识位。

**需求**：将话题预测接入已有 Agent 体系，基于近三十天星球发帖、提问与互动数据定时生成预测结果，产出进草稿箱人工确认后下发。

**验收标准**：预测结果由 Agent 任务产出，人工确认后前端更新；无产出时回退配置值。

### 5.2 头像墙

**现状**：星球动态详情有点赞能力，无点赞头像墙展示。

**需求**：星球动态详情在精华回答下方展示点赞用户头像墙（前 N 个头像叠加，超出计数）。

**验收标准**：点赞后头像墙实时更新，取消点赞同步移除。

### 5.3 群码轮换

**现状**：读者群二维码为后台人工维护。

**需求**：群二维码七天轮换自动化，满员群自动切换备用群；群码弹层展示有效期提示。同时验证资料预览的昵称与手机号水印叠加效果，确保与原型一致。

**验收标准**：到期自动更换群码且旧码有失效提示；水印在预览页正确叠加。

## 六、阶段二预留

### 6.1 UGC 发布器

数据结构自设计之初即按 UGC 准备（作者角色、审核状态字段齐备），阶段二仅需开放权限并新增发布编辑器。编辑器要求：三种内容类型（长文、笔记、动态）、图片九宫格、话题定位关联、同步星球开关、仅会员可见开关。本项不随阶段一交付，但相关字段改动不得破坏预留结构。

### 6.2 审核队列

阶段一内容发布已具备机器安检与人工放行口径；阶段二开放 UGC 后，用户内容一律进入审核队列，复核通过后方可公开。审核队列界面可延后开发，接口层面的审核状态流转需在 P0 评论盖楼开发时一并遵守。

## 七、五页装修化

### 7.1 整体口径

原型五个 Tab 页均可由装修页承载。当前绑定：首页、内容、星球、商城四个 Tab 已绑定装修页；「我的」为原生页并显式解绑装修页。

### 7.2 我的页方案

原型我的页（会员卡、继续学习、我的星球、提问打卡、成为创作者）与现有三皮肤模板库高度重合，优先通过模板库与动态菜单覆盖；确需完全还原原型排版的，再评估是否将「我的」重新绑定装修页，涉及切换需回归验证登录态与菜单动态化逻辑。

### 7.3 发现页对齐

发现页已按原型完成小红书化改造：类型大 Tab（笔记、长文、好物）、创作者招募横幅、投稿悬浮钮均已上线，无需重复开发，仅需按客户真实内容填充。

## 八、技术约束

### 8.1 安全底线

资料试读裁切必须在服务端完成后下发，禁止下发完整文件由前端遮挡；内容下架不收回已购权限，已购用户在「我的 - 已购内容」必须仍可阅读；AI 产出须经安全检查并进入草稿箱人工确认后发布。

### 8.2 微信约束

附件无本地下载落点，一律在线预览加转发留存；朋友圈不能直接转发小程序，只能生成海报图；支付回调必须幂等；登录为动作触发式弹层，浏览公开内容不拦截；订阅消息需用户主动触发且为一次性；iOS 端虚拟商品支付须遵循平台合规策略（系统已有对应策略服务，新增商品类型须接入）。

### 8.3 版本纪律

对已发布版本文件只增不改，变更以新增版本记录；数据库变更走 schema_version 迁移脚本，禁止手工改库；小程序上传前全部脚本过语法检查，主包体积逼近上限时新功能放分包。

## 九、交付顺序

### 9.1 排期建议

| 批次 | 内容 | 理由 |
|------|------|------|
| 第一批 | 支付幂等（4.2）+ 失败三态（4.3） | 资金安全，最难返工 |
| 第二批 | 评论盖楼（3.1）→ 笔记详情（3.3） | 存在依赖关系，顺序固定 |
| 第三批 | 音频形态（3.2） | 相对独立，可并行 |
| 第四批 | 海报模板（4.1）+ 无网络态（4.4） | 形态补齐 |
| 第五批 | P2 三项（5.1–5.3） | 增强，可进后续迭代 |
| 第六批 | 阶段二发布器（6.1） | 可延后，权限开放时再上 |

### 9.2 验收口径

每项功能交付须提供「原来是什么、现在是什么」的前后对照；上线前完成全量脚本语法检查与无头浏览器截图验证；涉及发布的页面以线上 DSL 与缓存版本号双核对为准。
