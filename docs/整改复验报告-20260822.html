一、本次新引入的问题

这部分优先看——都是整改过程中带进来的，其中前两条建议今天就处理。

N1迁移脚本的执行顺序是错的，全新库跑必失败

新增的 deploy/scripts/migrate.sh 思路对（schema_version 表 + 幂等跳过），但遍历用的是 bash glob：

for f in "$SQL_DIR"/V*.sql; do   # ← 字典序，不是版本序

实测该目录下的展开顺序是：V10 → V11 → … → V47 → V4__content_tables → V5 → …。也就是说 V16（给 mp_user 加列）会在 V11（建 mp_user）之前执行，V44（改 mp_content）会在 V4（建 mp_content）之前执行，全新库必然中途报错退出。

现有生产库因为 V1~V43 已手工执行过，只会跑 V44~V47，这四个恰好字典序也正确，所以暂时看不出问题——但只要有人用它初始化一套新环境（测试环境、新客户），立刻踩雷。

一行修复：for f in $(ls "$SQL_DIR"/V*.sql | sort -V); do。另外建议把它接进 server-rebuild-backend.sh，否则仍然依赖人记得手动跑；密码目前走命令行参数（-p"$DB_PASS"），在 ps 里可见，建议改用 MYSQL_PWD 或 defaults-file。

N2评论功能上线了，但没有内容安全检测，也没有后台管理入口

新增的 mp_content_comment 表默认 status TINYINT NOT NULL DEFAULT 1（1=可见），ContentInteractServiceImpl 里没有任何审核或过滤逻辑，全项目搜不到 msgSecCheck；后台 admin/src/views 下也没有任何评论管理页面。

这意味着：用户发的评论直接公开可见，没有敏感词拦截，出了问题运营也没有地方删。微信对小程序内的 UGC 有明确要求，未接内容安全接口的社区功能是审核驳回和封禁的高频原因。

建议（按紧急程度）：① 接微信 security.msgSecCheck（用已有的 WxMiniappTokenService 拿 access_token），命中即置 status=0；② 后台加一个评论列表页，支持隐藏/删除；③ 在这两项完成之前，如果要上线，先把评论入口关掉——现在的状态比没有评论更危险。

N3点赞/收藏会把整行内容回写，可能覆盖后台正在编辑的正文

ContentInteractServiceImpl.toggleLike：

int likeCount = content.getLikeCount() ...;
content.setLikeCount(likeCount + 1);
contentMapper.updateById(content);   // ← 全字段回写整行

两个问题叠加：一是计数走"先读后写"，并发点赞会丢更新（库存那边已经改成原子 SQL 了，这里是新写的代码又回到了老模式）；二是 updateById 会把这条内容的所有字段（含 MEDIUMTEXT 正文）按点赞时读到的快照写回去——如果此刻运营正好在后台保存了这篇文章，用户的一次点赞就能把编辑覆盖掉。

建议：改成 UPDATE mp_content SET like_count = like_count + 1 WHERE id = ? 的定向更新（收藏同理）。这也和库存修复保持同一套写法。

N4事件批量上报接口公开且不限条数

POST /api/v1/mp/events/batch 在 SecurityConfig 里是 permitAll，而 MpGrowthController.trackBatch 对 list 长度没有任何上限校验，直接 for 循环逐条落库。配合 max-request-size: 100MB，一次请求可以写入数万行 mp_analytics_event。

建议：单次限 50 条；给 /events* 单独设更严的 IP 限流；考虑改为需要登录（小程序用户几乎都有 token），匿名事件保留 page-access 那一条即可。另外事件表建议现在就定好保留期（如 90 天）和清理任务，否则半年后它会是最大的表。

N5监控两头没对上：指标端点要 super_admin，抓取端没配凭据

好消息是 actuator + micrometer 依赖加上了，management.endpoints.web.exposure.include: health,prometheus,info 也配了。但 SecurityConfig 里 /actuator/prometheus 是 .hasRole("super_admin")，而 deploy/monitoring/prometheus.yml 里这个 job 没有任何 authorization 配置 → 抓取会 401，Grafana 依然是空的。

建议：二选一——把 /actuator/prometheus 改为仅内网可达（compose 内网 + 不映射端口）并 permitAll；或给 prometheus job 配 authorization: { credentials: ... }。前者更简单。

N6主题换肤依赖一个可能不存在的 API，需要真机确认

新增的 miniapp/utils/theme.js 思路是对的：把主色算成一组 CSS 变量（含 brand-dark/soft/muted 派生色），让全站 371 处 var(--brand) 生效，app.wxss 的 --brand 也统一成了 #002FA7。

但注入方式是：

if (typeof wx.setPageStyle === 'function') { wx.setPageStyle({ style }) }

wx.setPageStyle 不在微信公开 API 列表里（页面级样式注入的公开做法是 <page-meta page-style="…">），而全项目没有任何页面使用 page-meta。由于外层有 try/catch 和"旧基础库无此 API，忽略"的注释，如果该 API 不存在，整个换肤会静默失效，看不出任何报错。

建议：务必用真机跑一次——改一次主色看小程序是否真的变了。如果没变，改为在每个页面根节点套 <page-meta page-style="{{themePageStyle}}">（Page hook 已经在往 data 里塞 themePageStyle 了，改造量很小）。

N7~N10其余四条较轻

· 容器内子组件的数据源不会加载：loadAllComponentData 只遍历顶层 components，不递归 children。当前容器只允许放分区标题/图片/富文本/卖点卡/间距这几种静态组件，所以暂时无碍；一旦允许把商品列表放进容器就会空白。

· 两处全局 Page 包装：theme.js 和 share.js 都重写了全局 Page，其中 theme 有 __themeHookInstalled 幂等标记，share 没有。建议补上，避免将来重复注册导致 onShow/onShare 被包两层。

· 退款金额换算漏改：MoneyUtils 已在下单与支付回调统一，但 RefundServiceImpl:189-190 仍是 multiply(100).intValue() 截断，没跟着改。

· 4 这个数字散在三处：TabBarEditor.vue、useMiniappConfig.ts 各定义一次 TABBAR_SLOT_COUNT = 4，小程序端 TAB_SLOT_ROUTES 是第三处。建议注释里互相指认，避免将来改一处漏两处。

三、半修复：两条"看起来修好了，其实没生效"

H1JWT 密钥的代码库默认值仍在生效

JwtTokenProvider 确实改好了：@Value("${jwt.secret:}") + 长度不足 32 拒绝启动。但 application.yml 里那行没删：

jwt:
  secret: ${JWT_SECRET:miniprogram-platform-jwt-secret-key-must-be-at-least-256-bits-long-for-hs256}

Spring 解析属性时，yml 里的值优先于 @Value 的冒号默认值——@Value 的 :"" 只在属性完全不存在时才用。所以 环境变量漏配时，签名密钥依然是这串写在开源代码里的字符串，而且它足够长，新加的长度校验也拦不住，反而给人"已经防住了"的错觉。

修复：把 yml 改成 secret: ${JWT_SECRET}（不带默认值），缺失时启动直接失败。这是一行改动，建议今天做。

H2compose 里仍有三处弱默认口令，数据库端口仍对宿主机开放

JWT 和 Redis 密码改成必填了，但同一个文件里：MYSQL_ROOT_PASSWORD:-root123456、MYSQL_PASSWORD:-miniapp123456、GRAFANA_PASSWORD:-admin123456 原样保留；3306:3306 与 6379:6379 也仍映射到宿主机。

修复：三处一并改 :? 必填；数据库与缓存端口去掉映射或绑定 127.0.0.1:3306:3306。
