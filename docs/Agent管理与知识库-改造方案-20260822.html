Agent 管理 + 知识库：改造方案

交付给开发执行 · 2026-08-22 · 基于 V48 内容 Agent 已上线后的最新代码

先更新一下现状：后端已经跑在前面了，缺的是前端入口和知识库后端

复核代码发现，多岗位 Agent 的后端基本已经就位：mp_agent_config.role 字段（V48）、getActiveConfigByRole()、publishConfig() 发布时按角色下线同角色其它配置、chatForRole() 按岗位取配置——都实现了。内容管理 Agent 的 13 项任务全部落地（A1~D3 + 自由指令），含任务表、明细表、进度、批量审核、采纳与回滚。执行得很扎实。

所以这份方案不是"新建两个功能"，而是补两个明确的缺口：

缺口一：前端还是单配置页，导致内容 Agent 在借用客服的模型和提示词。admin/src/api/agent.ts 的所有接口都不带 role，页面只能编辑一份配置。chatForRole("content_ops", ...) 找不到内容岗位的配置时会回退到客服配置（AgentConfigServiceImpl:258-261）——功能不报错，但内容 Agent 现在是拿着"你是客服"的提示词在做分类和写摘要。

缺口二：知识库仍是空壳。uploadKnowledge 只做两件事——存文件、插一条记录，没有解析、切片、检索；回答链路里知识一个字都没进去。

⚠ 顺带发现一个安全问题（建议一并修）：知识库文件用 fileUploadService.upload(file) 单参数版本上传（AgentConfigServiceImpl:504），没有传 subDir，文件落在 /uploads/{日期}/{uuid}.ext——而 /uploads/** 是 permitAll 的公开静态目录。内部知识资料任何人拿到 URL 就能下载。改法：传 "protected" 作为 subDir（ProtectedUploadFilter 已能拦截该目录的直接访问），并改为通过带鉴权的接口下载。

A1　后端改动（小）

1. 配置列表支持按角色过滤——AdminAgentController 的 GET /api/v1/admin/agent 增加可选参数 role。

2. 新增岗位清单接口 GET /api/v1/admin/agent/roles，返回：

[
  { "role":"service",      "name":"客服助手",   "configured":true,
    "activeConfigId":3, "model":"deepseek-chat", "updatedAt":"..." },
  { "role":"content_ops",  "name":"内容运营",   "configured":false,
    "activeConfigId":null, "fallbackTo":"service" },   // ← 前端据此给出「未配置，正在借用客服配置」的警示

3. 创建配置时接受 role——POST /api/v1/admin/agent 的 DTO 里 role 字段已有（AgentConfigDTO:13），确认保存链路没有把它丢掉即可。

4. 回退时打警告日志——chatForRole 走到回退分支时 log.warn("岗位 {} 未配置模型，已回退到客服配置", role)，便于运维发现。

合计约 3 小时。后端的数据模型不用动，V48 已经把地基打好了。

A2-2现有配置页改成按岗位加载

admin/src/api/agent.ts 全部接口加 role 参数；views/ai/agent/index.vue 从路由取 role 后加载对应配置。六个 tab 的内容不动，只在页头加一个岗位标识和返回列表的入口。

A2-3新建 Agent 从岗位模板起步

点「立即配置」时，预填该岗位的推荐配置，运营只需填 API Key：

岗位预置 system_prompt 要点推荐参数
客服助手身份、答不上来必须说转人工、禁止承诺价格与时效、只依据知识库回答temperature 0.3，max_tokens 512
内容运营身份、品牌调性、分类与标签必须从给定清单里选、输出 JSON、不确定就返回低置信度temperature 0.2，max_tokens 2048
页面搭建（预留）只输出符合 schema 的 DSL、组件只能用给定清单temperature 0.1

为什么模板重要：内容 Agent 的提示词要求"输出 JSON、分类从清单里选、不确定给低置信度"，和客服的完全不同。没有模板，运营大概率会照抄客服的那份，然后发现效果很差。

A3　新增三个 tab（可在 A2 之后分批做）

⑦ 工具授权——先做展示 + 开关，不做完整 Tool Registry。列出该岗位能调用的能力（内容 Agent：改元数据 / 改正文 / 挂商品 / 定时发布），每项三档：仅建议 / 可改草稿 / 可执行，以及「是否需人审」。存进 mp_agent_config 新增的 tool_grants JSON 字段即可，不用建表。

这一步的价值不在技术，在让授权边界变成看得见的配置——现在这些规则散在代码里（比如已发布内容不许改正文那条硬编码在 ContentAgentTaskServiceImpl:339）。

⑧ 成本与配额——展示按天/按岗位的调用次数与 token 消耗，配置日预算上限与超支行为（告警 / 停机）。数据来源：新增一张 mp_agent_call_log（agentRole / model / promptTokens / completionTokens / costEstimate / latencyMs / taskId / success），在 chatForRole 和 chat 里各埋一行。

④ 沙盒测试升级为评测集——保留单条试问，增加「批量评测」：维护 20~50 条用例（输入 + 期望要点），一键跑分并与上一版本并排对比。建议本期就做最简版：用例存 JSON、跑完人工打勾，先不做自动 judge。

Part B　知识库：先补后端，再做界面

B0　立刻要做的一件小事（半天）

在现有「③ 知识库」tab 顶部加一条醒目提示：

⚠ 知识库文件已保存，但尚未接入回答链路。
   当前 AI 回答仅依据「② Prompt 配置」中的提示词。

同时把上传路径改到 protected 子目录（见文首安全问题）。

为什么先做这个：运营现在会传文件、设权重，然后以为生效了。诚实标注的成本是半天，误导的成本是他们对整个 AI 能力失去信任。

B1　最小可用 RAG（后端，本方案核心）

B1-1新增切片表

CREATE TABLE mp_agent_knowledge_chunk (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  knowledge_id BIGINT NOT NULL COMMENT '所属知识源',
  config_id    BIGINT NULL     COMMENT '所属 Agent 配置（沿用 V35 已加的 config_id 语义）',
  seq          INT NOT NULL    COMMENT '切片序号',
  title        VARCHAR(255)    COMMENT '所属小节标题，召回时一并给模型',
  body         TEXT NOT NULL   COMMENT '切片正文',
  char_len     INT NOT NULL DEFAULT 0,
  source_ref   VARCHAR(500)    COMMENT '出处：文件名#段落 或 内容ID',
  hit_count    INT NOT NULL DEFAULT 0 COMMENT '被召回次数',
  create_time  DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_knowledge (knowledge_id),
  FULLTEXT KEY ft_body (title, body) WITH PARSER ngram
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='知识库切片';
中文全文检索必须加 WITH PARSER ngram，否则 MySQL 默认按空格分词，中文一个词都切不出来，检索永远返回空。同时确认 ngram_token_size（默认 2）符合预期。这是这一步最容易踩的坑。

B1-2解析与切片

新增 service/knowledge/KnowledgeIngestService.java：

  • 解析：.txt / .md 直接读；.html 用 jsoup（pom 已有）取正文；.docx / .xlsx 用 poi-ooxml（pom 已有）；.pdf 需要新增 pdfbox 依赖——如果不想加依赖，就在上传时明确拒绝 PDF 并提示"请转成 Word 或 Markdown"，不要静默失败。
  • 切片：优先按标题（h1~h3 / Markdown # ）切，再按段落合并到 500~800 字，相邻切片重叠 100 字避免语义断裂。每片记录所属标题。
  • 状态机：复用现有 vector_status 字段（pending → processing → done / failed），失败要写明原因。
  • 异步执行：复用已有的 importExecutor 线程池 + Redis 进度（与公众号导入同一套机制）。

B1-3检索与注入

// KnowledgeRetrievalService.retrieve(role, question, topK)
SELECT id, title, body, source_ref,
       MATCH(title, body) AGAINST(? IN NATURAL LANGUAGE MODE) AS score
FROM mp_agent_knowledge_chunk c
JOIN mp_agent_knowledge k ON k.id = c.knowledge_id
WHERE (c.config_id IS NULL OR c.config_id = ?)
  AND MATCH(title, body) AGAINST(? IN NATURAL LANGUAGE MODE)
ORDER BY score * k.recall_weight DESC     -- 复用已有的 recall_weight 字段
LIMIT ?

在 AgentConfigServiceImpl 的 chat 与 chatForRole 里，把召回结果拼进 system message：

【参考资料】（回答必须依据以下资料，资料中没有的信息请说明你不确定）
[1] {title}：{body}
[2] ...
回答末尾用 [1][2] 标注引用来源。

三条硬性要求：

  1. topK 默认 4，总长度上限按 token 预算截断——塞太多反而稀释重点，还烧钱。
  2. 召回为空时不要硬编——提示词里明确"没有相关资料时应告知用户并建议转人工"。
  3. 返回值带 sources，前端沙盒和小程序端都能展示"依据了哪几条知识"。

同时把召回到的切片 hit_count + 1（异步累加，别阻塞回答）。

B2　从内容库同步知识（这一项最有价值）

你已经有一整个内容库——导入后的公众号文章、问答库、商品与活动信息。不该让运营把系统里已有的内容导出成文档再传回来。

数据模型：mp_agent_knowledge 加两个字段：

source_type VARCHAR(16) NOT NULL DEFAULT 'file'   -- file|content|qa|product|manual
source_id   BIGINT NULL                            -- 对应业务表主键

同步配置（放在知识库管理页）：

☑ 已发布内容    分类：[跨境合规] [税务] [物流]  （不选=全部）
☑ 已采纳问答    （mp_question + mp_answer，status=answered）
☐ 商品说明
☐ 活动规则
[立即同步]   上次同步：2026-08-22 14:03 · 187 篇 · 1,240 个切片

实现要点：

  • 正文用 jsoup 转纯文本后再切片（HTML 标签进知识库是纯噪音）
  • source_ref 存内容 ID 和标题，将来可以做「点击引用跳到原文」
  • 增量更新：按 mp_content.update_time 比对，只重建变更过的；内容删除时同步删切片
  • 问答对不用切片，一问一答直接作为一个 chunk，检索命中率最高
  • 同步是手动触发 + 可选定时（每日一次），不要做成实时——没必要，还会拖慢内容保存

这是你相对通用 Agent 平台的独有优势：别人的知识库要从零喂，你的开箱就有一整个持续更新的内容库。客服 Agent 上线第一天就能回答"跨境电商 0110 报关怎么做"——因为你正好有那篇文章。

B3　知识库管理界面

做到这一步，界面才有意义。建议独立成 /ai/knowledge 页面（不再挤在 Agent 配置的 tab 里，因为知识是跨 Agent 共享的）：

模块内容优先级
知识源列表名称 / 来源类型 / 切片数 / 生效状态 / 最后更新 / 累计命中次数 / 召回权重 / 授权给哪些 Agent必做
检索测试输入问题 → 展示召回的 top5 切片与分数（不调模型，纯检索，快且免费）必做
切片预览点开知识源看被切成了什么样，支持手动合并/删除某片必做
手动问答录入一问一答直接入库，不必写成文档再上传必做
内容库同步B2 的勾选面板 + 同步进度必做
零命中清理筛出长期零命中的切片，一键停用可选

「检索测试」是这一页最有用的工具。当运营抱怨"AI 答得不对"，第一步就是在这里输入那个问题——看是召回错了（知识库问题）还是召回对了但答歪了（提示词问题）。没有它，排查全靠猜。

验收标准

Part A 与 Part B 可分别验收。

Part A

  • Agent 列表能看到三个岗位，未配置的岗位有明确警示
  • 给「内容运营」单独配置模型与提示词后，chatForRole("content_ops") 不再回退到客服配置（看日志确认无 warn）
  • 客服与内容运营各自发布版本互不影响（发布其一，另一个仍是启用状态）
  • 新建岗位时提示词模板已预填
  • 成本 tab 能看到分岗位的当日调用次数与 token

Part B

  • 上传一份 docx，能看到解析出的切片列表，状态为「已生效」
  • 知识库文件不再能通过 /uploads/ 直接下载
  • 检索测试输入中文问题能返回相关切片（验证 ngram 分词器生效）
  • 沙盒对话中问一个只有知识库里才有答案的问题，AI 能答对并标注引用来源
  • 知识库里没有的问题，AI 明确说不确定并建议转人工，不编造
  • 从内容库同步后，问一个只有某篇公众号文章里才有的细节，能答对
  • 修改一篇内容后重新同步，只有该篇的切片被重建
  • 切片的 hit_count 随召回累加

本次不做

  • 不上向量库。先用 MySQL 全文检索把链路跑通，效果不够再换 pgvector / Milvus。中文客服场景关键词召回往往已经够用，而且省一整套基础设施。切片表设计已经为将来加 embedding 列留了余地。
  • 不做完整 Tool Registry。先用 tool_grants JSON 把授权变成可见配置，等第三个岗位上线再抽象成表。
  • 不做多模型路由。等有第二个供应商的实际需求时再做适配层——现在做是过早抽象。
  • 不做知识库的自动质量评分。先让「命中次数」和「检索测试」跑起来，人看得见就够了。
