一、本轮新引入 / 需要立刻处理

X1指标端点公网可读

三个条件同时成立：

① SecurityConfig:100 → .requestMatchers("/actuator/prometheus").permitAll()（上轮还是 hasRole("super_admin")）；
② deploy/nginx/default.conf:102 有 location /actuator/ 直通后端，注释里写着"生产环境应限制访问 IP"，但 allow/deny 四行全是注释；
③ docker-compose.yml:104 → "${BACKEND_PORT:-8080}:8080"，未绑 127.0.0.1（MySQL 和 Redis 这轮都绑了，后端漏了）。

暴露的内容包括 JVM 内存与线程、HTTP 各路径的请求量与耗时分布（等于把接口清单和流量结构公开）、数据库连接池状态。/actuator/health 同样 permitAll，好在 show-details: when_authorized 限制了细节。

三选一，任一即可：① nginx 里取消那四行注释；② compose 改成 "127.0.0.1:${BACKEND_PORT:-8080}:8080"（与本轮 MySQL/Redis 的处理保持一致，最省事）；③ 配 management.server.port 走独立内网端口。改完确认 curl https://你的域名/actuator/prometheus 返回 403 或不可达。

git status：130 个 M、69 个 ??、6 个 D，最近一次提交还停在整改之前的 0a5c539。这几轮所有整改——支付验签、评论合规、容器组件、流程重设计、四个新迁移——全部只存在于工作区。

X3支付回调仍不限流，且未知 serial 会触发对微信的证书拉取

验签本身写得很好，但两处配合起来有放大风险：RateLimitFilter.shouldNotFilter 仍把两个回调路径完全排除在限流外；而 WxPayNotifyVerifier.resolvePublicKey 遇到未知 serial 会把 certCacheAt 归零并强制刷新一次平台证书（一次对 api.mch.weixin.qq.com 的出站请求）。

也就是说：外部只要不断用伪造的 Wechatpay-Serial 打这个公开端点，就能驱动后端不停地去请求微信的证书接口，可能触发微信侧频控，进而影响真实回调的验签。

建议：给回调路径加一个宽松但存在的限流（例如 300 次/分钟）；证书强制刷新加节流（同一分钟内最多一次），未知 serial 直接拒绝而不刷新。

X4微信 access_token 是进程内缓存，多实例会互相挤掉

WxMiniappTokenServiceImpl 用 volatile 字段 + synchronized 缓存 token。access_token 在微信侧是账号级单例，多个实例各自申请会让先拿到的失效。现在 msgSecCheck（评论合规）和订阅消息都依赖它——多实例部署时会出现评论校验和消息下发间歇性失败。

建议：单实例期间无碍，但在扩容前改成 Redis 共享缓存（提前量留好，别等出问题）。
