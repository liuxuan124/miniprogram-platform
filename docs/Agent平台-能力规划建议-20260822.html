Agent 平台：能力规划建议

从「一个客服助手」到「多岗位 Agent + 多模型」· 2026-08-22

先纠正三个认知：现在的 Agent 比字段名看起来的要单薄

① 知识库不参与回答。mp_agent_knowledge 目前只有增删查和权重字段，AgentConfigServiceImpl 里没有任何检索或拼接逻辑，vector_status 只是个状态位、没有向量化流程。也就是说客服现在完全靠 system_prompt 在答，知识库是个登记表。

② 对话是单轮的。调用时 messages 里只有 system + 当前问题，不带历史。memory_type 那个 short/long/hybrid 字段目前没有实现对应逻辑。

③ api_key_encrypted 只是列名，实际是明文存取，代码里没有任何加解密调用。

说这些不是挑毛病——是因为你接下来要做的三件事（页面搭建 Agent、客服 Agent、多模型），恰好每一件都踩在这三个空白上。下面按「不补就不成立 / 决定好不好用 / 做大了才需要」三档给建议。

第一梯队 · 不补就不成立

这四块是地基。没有它们，多 Agent 只能靠复制粘贴配置，多模型只能靠改代码。

P1数据模型：从单例改成多 Agent

现在是「一个 active config」。要改成：

mp_agent            -- 一个 Agent 就是一个岗位
  id / code(content_ops|customer_service|page_builder) / name / avatar
  status / description / systemPrompt / modelProfileId / version

mp_agent_tool       -- 这个 Agent 被授权了哪些能力
  agentId / toolCode / authLevel(suggest|write_draft|execute) / needReview

mp_agent_knowledge_rel  -- 知识库多对多（现在是全局共享，要能按 Agent 隔离）
  agentId / knowledgeId / recallWeight

关键判断：Agent 的身份是岗位，不是模型。同一个岗位可以换模型，同一个模型可以服务多个岗位。所以模型配置要从 Agent 里拆出去（见 P3）。

P2工具层（Tool Registry）——这是 Agent 平台真正的心脏

「Agent 能干什么」不该写在提示词里，而应该是一份可授权、可审计、有 schema 的工具清单。把系统已有能力封装成 tool：

类别工具举例默认授权
内容查内容、改元数据（分类/标签/摘要/SEO）、生成正文、挂载商品、内容质检write_draft
页面读组件清单、生成页面 DSL、校验 DSL、存草稿、生成预览二维码write_draft
交易查订单、查物流、查库存suggest（只读）
高危发券、发起退款、改价格、发布上线needReview 强制人审
数据查搜索热词、查内容效果、查转化漏斗suggest

每个 tool 声明：入参 JSON Schema、授权等级、是否幂等、是否需人审、预估成本。模型只能调用被授权的 tool，越权直接拒绝并记录。

为什么这块最重要：没有工具层，Agent 就只能"说"不能"做"，你要的页面搭建和内容处理都落不了地；有了工具层，加一个新岗位只是配一份工具授权，不用改代码。

P3模型路由层（多供应商适配）

现在是写死的 OpenAI 兼容 /chat/completions。要接「全球各个模型」，需要一层适配：

mp_model_profile    -- 模型档案，与 Agent 解耦
  id / name / provider(openai|anthropic|gemini|deepseek|moonshot|zhipu|qwen|doubao|spark)
  baseUrl / modelId / apiKeyRef / maxTokens / temperature
  supportsTools / supportsJsonSchema / supportsVision
  inputPricePer1k / outputPricePer1k / region(cn|global)

四个必须处理的差异点：

  • 函数调用格式不统一：OpenAI 的 tools、Anthropic 的 tool_use、Gemini 的 functionDeclarations 三套结构完全不同。适配层要做双向转换——这是接多模型工作量的大头，不是换个 baseUrl 那么简单。
  • 结构化输出能力不同：页面搭建 Agent 依赖严格 JSON 输出，要按 supportsJsonSchema 选模型，不支持的走「提示词约束 + 校验重试」降级。
  • 降级链：主模型超时/限流 → 备用模型 → 规则兜底。配置成 primary + fallback[]，不要在业务代码里写 if。
  • 境内外分流：境外模型的网络出口、延迟、以及数据出境合规。建议明确一条：C 端客服只用境内模型，境外模型只用于后台内容生产——用户对话数据出境是实打实的合规风险。

按任务选模型才是多模型的价值：批量打标签用便宜快的，写长文用强的，页面 DSL 用结构化输出好的，客服用延迟低的。建议在 Agent 上配「任务类型 → 模型档案」的映射，而不是一个 Agent 绑死一个模型。

P4密钥与成本

· 密钥：现在明文存库。至少改成环境变量注入 + 库里只存引用（apiKeyRef），或用 AES 加密 + 密钥走环境变量。后台展示一律脱敏，测试连通性用后端持有的真值。

· 成本记账：每次调用落一条记录——agent / 模型 / 输入输出 token / 耗时 / 估算费用 / 是否命中缓存。没有这个，多模型跑起来你不知道钱花在哪。

· 预算熔断：按 Agent 和按天设上限，超了自动停并告警。批量任务 × 长文很容易失控。

· 缓存：相同输入 + 相同模型 + 内容未变 → 直接复用结果。内容类批处理的重复率比想象中高。

第二梯队 · 决定好不好用

P5RAG 真正落地（客服 Agent 的前提）

现在的知识库不参与回答，所以客服的知识全靠提示词硬塞，改一次知识要改一次提示词。完整链路需要：文档切片 → 向量化 → 存储 → 召回 → 重排 → 拼进上下文 → 回答带出处。

务实的做法：先做关键词检索版（MySQL 全文索引 + 分词），把「知识能进回答」这条链路先跑通，再换向量库。很多客服场景关键词召回的效果已经够用，而且没有额外基础设施成本。

一个容易忽略的点：回答要带出处（引用了哪篇知识的哪一段）。这既是让人敢信的基础，也是发现"知识库写得不对"的唯一途径。

P6多轮记忆与会话管理

现在每次只发当前问题，用户说「那第二个方案呢」模型完全接不住。需要：短期记忆（最近 N 轮，按 token 预算截断）+ 长期记忆（用户画像摘要，如"跨境卖家、关注合规"）+ 转人工衔接（把上下文一并交给客服，is_transfer_human 字段已有）。

P7评测与回归（这是团队做 Agent 最容易缺的一块）

提示词改了一版，怎么知道是变好还是变坏？现在只能凭感觉。建议建一套最小评测：

  • 每个 Agent 维护 30~50 条评测集（典型问题 + 期望要点，不必是标准答案）
  • 改配置后一键跑分，用另一个模型当 judge 打分（相关性/准确性/是否越界）
  • 上线前把新旧版本的输出做并排 diff，人工扫一眼
  • 把线上被人工驳回的 case 自动沉淀进评测集

成本很低但收益极高：没有评测，提示词优化就是碰运气，而且改坏了没人发现——直到运营开始抱怨。

P8可观测

每次调用记录完整链路：请求内容、命中的知识、调用了哪些工具及参数、模型返回、token 与费用、耗时、人工是否驳回。后台给一个 Agent 工作台：今日任务数、成功率、平均耗时、成本、驳回率 Top 原因。驳回率是最重要的指标——它直接告诉你这个 Agent 值不值得提权。

两个岗位的特殊要求

页面搭建 Agent（三个岗位里最难的）

难在输出必须严格合法。DSL 有 37 个组件、每个组件一套 props、还有容器嵌套——让模型自由生成 JSON 必然出错。四条建议：

  1. 用结构化输出而非自由文本：把 componentRegistry.ts 导出成 JSON Schema，走 function calling 或 json_schema 模式强约束。这也是选模型时要看 supportsJsonSchema 的原因。
  2. 生成后必须过校验再落库：复用现有的 validateComponent 和发布前 preflight。校验失败把错误信息回喂给模型重试，最多 2 次。
  3. 分步生成而不是一次成页：先定骨架（页面类型 + 分几个区 + 每区放什么组件），再逐区填充 props。一次生成整页的成功率远低于分步。
  4. 给模型看的组件说明要单独写：不是把 TS 类型扔给它，而是每个组件配一句「适合什么场景、什么时候不要用」。这份说明本身就是提示词工程的主要工作量。

产出永远是草稿 + 预览二维码，人扫码看过才能上线。这条不要妥协。

客服 Agent

· RAG 是前提（P5），否则知识只能硬编码在提示词里。

· 工具分级很关键：查订单、查物流可以自动执行；发券、退款必须转人工确认。这正是 P2 授权等级的用武之地。

· 兜底要诚实：答不上来就说「这个我不确定，帮您转人工」，不要编。宁可转人工率高一点，也不要一次错误答复。

· 会话质检：每天抽样若干条，用另一个模型打分，低分的进人工复核。

· 合规：C 端对话建议只走境内模型。

建议的路线

阶段内容产出
一期P1 多 Agent 模型 + P2 工具层骨架 + P3 模型路由（先接 2~3 家）+ P4 密钥与成本内容管理 Agent 真正跑起来，把存量草稿处理掉
二期P5 RAG（先关键词版）+ P6 多轮记忆 + P8 可观测客服 Agent 从「靠提示词」变成「靠知识库」
三期页面搭建 Agent（结构化输出 + 校验重试 + 分步生成 + 预览）一句话生成可编辑页面初稿
四期P7 评测体系 + 灰度 A/B + 注入防护补全从「能用」到「能持续优化」

P7 评测虽然排在四期，但建议一期就先建一个最简版（每个 Agent 20 条评测集 + 手动跑）。等到三个 Agent 都上线再补，那时改任何提示词都会变成不敢动的状态。

三个「别做」

  • 别做「什么都能干」的通用 Agent。按岗位定义能力边界，一个岗位一套工具授权。通用 Agent 的结果通常是什么都干不好，而且没法授权——因为你不知道它会去动什么。
  • 别让 Agent 直接操作生产数据。永远走「产出 → 审核 → 应用」，哪怕将来提权到自动执行，也要保留完整留痕和一键回滚。
  • 别一上来接十家模型。先接 2~3 家（一个境内主力、一个境外强模型、一个便宜的批量模型）把适配层跑通。函数调用格式的差异比想象中麻烦，接第四家时你会庆幸前三家的抽象做对了。
本建议基于 2026-08-22 的代码实况：mp_agent_config 为单例配置（模型/提示词/温度/知识库/版本/连通性测试），调用走 OpenAI 兼容 /chat/completions；知识库无检索实现、对话无历史、API Key 明文存储——这三点已在文首说明。mp_agent_version、mp_ai_conversation（含转人工标记）、页面 DSL 校验与 preflight 均可作为新架构的复用基础。
