公众号导入内容：样式还原改动方案

交付给开发执行 · 2026-08-22 · 解决「导入后与公众号原文差距很大」

结论：不是微信排版太复杂，是导入链路上有三处代码在主动删内容，其中两处是 bug

排查结果：正文图片的地址被删光了（最致命，整篇图片消失）、文章开头被整段裁掉、开头一到两张图被当作 banner 删除，另外排版参数完全没对齐（mp-html 的 container-style / tag-style 一个都没传，且旧的图片样式选择器已失效）。

前四项都能修好，第一项改一行正则就能让图片全部回来。第五项（公众号内嵌视频、style 块、伪元素）属于渲染器能力边界，只能降级处理。

另外：这套清洗逻辑在 miniapp/utils/article-content.js 和 admin/src/utils/article-content.ts 各写了一份，逻辑完全相同。每一处改动两边都要同步改，否则后台预览与真机会不一致。

⚠ 施工顺序警告：R1 和 R3 必须在同一批次改，不能只改 R1。
现在 stripLeadingBannerImages 用的正则要求 src=，而公众号图片只有 data-src，所以它目前根本没生效。一旦按 R1 把 data-src 改写成 src，这个删图逻辑会立刻被激活——图片刚回来就又被删掉首图。两项必须一起上线。

R1　正文图片全部不显示 最高优先级

成因

公众号正文的图片标签通常是 <img data-src="https://mmbiz.qpic.cn/..." class="rich_pages" style="...">——只有 data-src，没有 src（微信自己的懒加载机制）。

链路在两个地方接不上：

  1. 后端 rewriteHtmlImages（1047~1066 行）把 data-src 的值换成转存后的本地地址，但属性名原样保留，仍是 data-src。
  2. 小程序端 miniapp/utils/article-content.js:165 的 cleanupWechatEditorMarkup 有一行 .replace(/\sdata-[a-z0-9-]+="[^"]*"/gi, '')，把所有 data-* 属性删光。

结果：<img> 既没有 src 也没有 data-src，整篇文章的图片全部消失。

这也解释了为什么「贴图形式还行、文章形式差得远」——这套清洗只在 !isNote 时执行（content-detail.js:326），笔记不走这条路。

改法

在后端输出时统一把属性名规范化为 src。修改 WeChatOfficialAccountContentSyncServiceImpl：

// 第 54 行：正则增加一个捕获组，把属性名单独捕获出来
- "(<img[^>]*?\\s(?:src|data-src)\\s*=\\s*[\"'])([^\"']+)([\"'][^>]*>)"
+ "(<img[^>]*?\\s)(?:src|data-src)(\\s*=\\s*[\"'])([^\"']+)([\"'][^>]*>)"

// rewriteHtmlImages（1051 行）里改写时固定输出 src
+ String replacement = prefix + "src" + eq + mirrored + suffix;

注意：IMG_SRC_PATTERN 还被 extractImageUrlsFromHtml（969 行）使用，改捕获组编号后那里的 group(2) 要同步改成 group(3)，否则取到的是等号而不是 URL。这是最容易漏的一处。

兜底：前端 cleanupWechatEditorMarkup 的 data-* 清理保留，但把 data-src 排除在外，防止历史已入库的数据仍是 data-src：

- .replace(/\sdata-[a-z0-9-]+="[^"]*"/gi, '')
+ .replace(/\sdata-src=(["'])([^"']*)\1/gi, ' src=$1$2$1')   // 先转成 src
+ .replace(/\sdata-[a-z0-9-]+="[^"]*"/gi, '')                // 再清其余 data-*

存量数据处理：已经导入的 6 篇（以及后续的）正文里存的是 data-src。上面的前端兜底能让它们正常显示；如果想彻底清干净，写一个一次性 SQL 或脚本把 mp_content.content 里的 data-src= 批量替换成 src= 即可，改动幂等。

R2　文章开头被整段裁掉

成因

stripWechatEditorPreamble（article-content.js:122）的逻辑是：只要正文前 12000 字符内出现 <h2> 且不在开头，就执行

return result.slice(sectionStart >= 0 ? sectionStart : h2Index)

也就是从第一个 h2 之前最近的 <section> 处直接截断，前面全丢。对于「导语 + 首图 + 小标题」这种最常见的结构，开头的导语和首图会被整块删除。

而且函数里的判断规则是针对某一个特定模板硬编码的——它在找 周报|WEEKLY|第\d+期 关键词，还有一条写死的背景色 #2A1F14。这明显是当初为某个号的固定版式调的，套到普通文章上就变成了误删。

改法

把「默认裁剪」改成「命中特征才裁剪」：

  1. 删掉最后那句无条件的 return result.slice(...) 兜底——只有 looksLikeMasthead 为 true 时才裁。
  2. looksLikeMasthead 的判定条件收紧：必须同时满足「h2 之前的纯文本 ≤ 300 字」且「与标题高度重合或命中刊头关键词」。现在的 900 字上限太宽松。
  3. 硬编码的 周报|WEEKLY|第\d+期 和 #2A1F14 抽成配置项，见下面的「配置化建议」。
  4. 保留 removeDuplicateBodyHeadings（去掉与标题重复的 h1）——这条是合理的，误伤概率低。

判断原则：删内容这件事，宁可少删也不要多删。多留一段刊头，运营看一眼就能手动删；删错了正文，运营根本不知道丢了什么。

R3　开头 1~2 张图被当作 banner 删除

成因

prepareArticleContentHtml 里调用 stripLeadingBannerImages(out, 2)：无条件删掉开头第一张图（i === 0 分支直接删），第二张图在剩余正文 ≥ 60 字时也删。作者习惯用大图开篇的话，那张图就没了。

改法

默认关闭，改为可配置：

- out = stripLeadingBannerImages(out, 2)
+ out = stripLeadingBannerImages(out, options.stripBanner ?? 0)   // 默认不删

同时 stripLeadingDuplicateCoverImages（删与封面重复的首图）保留——这条判断有明确依据（URL 与封面相同），误伤概率低，而且能避免封面和首图重复展示。

再次提醒：该函数的正则 LEADING_IMG_RE（第 69 行）要求 src=。R1 生效后它才会真正开始工作——所以 R1 和 R3 必须同批上线，否则会出现「图片刚修好，首图又被删」。

R4　排版参数没对齐

成因

其一：content-detail.wxml:196 调用 mp-html 时只传了 lazy-load / selectable / show-img-menu / domain，而 mp-html 支持的 container-style、tag-style、scroll-table、use-anchor 一个都没传，正文排版完全靠原文内联样式，缺失的地方用组件默认值。

其二：content-detail.wxss:686 的 .a-body rich-text image { max-width:100%; border-radius:16rpx; margin:16rpx 0 24rpx } 是给旧的 <rich-text> 写的。换成 mp-html 之后页面上已经没有 rich-text 节点，这条规则永远不命中——图片的宽度限制、圆角、上下间距全部失效。

其三：.a-body 设的是 font-size: 32rpx（16px）、line-height: 1.88，而微信正文是 17px / 1.6 左右。

改法

用 mp-html 的属性传样式，不要去改 wxss 选择器——自定义组件有样式隔离，从页面样式去够组件内部节点既不可靠也难维护。

<mp-html
  content="{{article.content || article.body}}"
  container-style="{{bodyContainerStyle}}"
  tag-style="{{bodyTagStyle}}"
  scroll-table
  lazy-load selectable show-img-menu domain="" />

在 content-detail.js 里按 layoutTheme 生成（正文排版主题字段 layout_theme 已存在，V45 加的，现有 theme-magazine / minimal / large 三档正好复用）：

const BODY_STYLE = {
  standard: {
    container: 'font-size:34rpx;line-height:1.75;color:#2b2f38;',
    tag: {
      p:   'margin:0 0 24rpx;',
      img: 'max-width:100%;border-radius:12rpx;margin:16rpx 0 24rpx;display:block;',
      h2:  'font-size:38rpx;font-weight:700;margin:40rpx 0 20rpx;',
      h3:  'font-size:36rpx;font-weight:600;margin:32rpx 0 16rpx;',
      blockquote: 'border-left:6rpx solid #d5dae3;padding-left:20rpx;color:#5e6673;margin:24rpx 0;',
      table: 'width:100%;border-collapse:collapse;',
      td:  'border:1rpx solid #e2e6eb;padding:12rpx;',
    },
  },
  magazine: { ... }, minimal: { ... }, large: { ... },
}

同时删除 .wxss:681-690 那两条已失效的 .a-body rich-text 规则，避免误导后来的人。

参数建议：字号 34rpx（17px）、行高 1.75、段间距 24rpx、正文色 #2b2f38 —— 这组值接近微信正文观感。上线后拿真机对照微调即可。

R5　微信特有元素（能力边界，做降级）

mp-html 的 ignoreTags 包含 iframe / script / style / input / textarea 等，所以以下内容无法还原，这是渲染器的边界，不是 bug：

  • 公众号内嵌视频（iframe / mpvoice 音频）
  • <style> 块里定义的类样式（只有内联 style 生效）
  • 伪元素装饰、部分绝对定位与复杂 flex 排版
  • 投票、小程序卡片、名片等微信独有组件

建议做法

  1. 导入时检测并标记：正文含 iframe/mpvoice/style 块时，在导入结果里列为「需人工处理」，而不是静默丢弃。这一条可以直接并入内容管理 Agent 的「导入质检」任务。
  2. 视频降级：把 iframe 的 src 提取出来存进 video_url 字段（V45 已有），详情页用原生 <video> 播放——很多公众号视频其实能提取到直链。
  3. 其余情况：在编辑页给出提示「本文含微信特有元素 N 处，建议人工调整」，让运营心里有数。

配置化建议（避免下次又写死）

把清洗策略做成后台可配，放在系统设置 → 内容导入下，而不是硬编码在代码里：

配置项默认值说明
删除开头图片数00=不删；用大图开篇的号设 1
裁剪刊头关开启后才执行 R2 的截断
刊头关键词空逗号分隔，替代写死的「周报/WEEKLY/第N期」
刊头背景色空替代写死的 #2A1F14
去除与标题重复的 h1开这条误伤低，保持默认开
正文排版主题standard已有 layout_theme 字段，作为导入默认值

为什么值得做：不同公众号的版式差异很大，写死任何一套规则都会在另一个号上翻车。做成配置后，换客户只改配置不改代码。

验收标准

测试方法：挑 3 篇结构不同的原文——① 导语+首图+多个小标题 ② 纯图文混排无小标题 ③ 含表格或引用块——导入后与公众号原文并排截图对比。

  • 正文所有图片正常显示，不再有空白占位
  • 文章开头的导语段落完整保留，没有被截断
  • 开篇大图保留（配置为不删时）
  • 封面与正文首图重复时，正文首图仍被正确去重
  • 正文字号、行距、段间距与公众号原文观感接近
  • 图片有圆角与上下间距，宽度不溢出屏幕
  • 含表格的文章，表格可横向滚动不挤压
  • 已导入的存量内容（那 6 篇）刷新后图片也能显示
  • 后台预览面板与真机效果一致（两端逻辑同步改到位）
  • 含 iframe 视频的文章，导入结果里被标记为「需人工处理」

工作量与顺序

  1. R1 + R3 同批（后端 1 行 + extractImageUrlsFromHtml 组号 + 两端前端兜底与开关）：约 2 小时。先做这个，效果最直观。
  2. R4（mp-html 传参 + 四套主题样式 + 清理失效 wxss）：约 0.5 天
  3. R2（收紧裁剪逻辑，两端同步）：约 0.5 天
  4. 配置化 + R5 降级标记：约 0.5 天
  5. 三篇对照验收：约 2 小时

合计约 2 人天。
