搭建器与内容模块：组件级细化升级建议

微信小程序多场景搭建与运营系统 · 2026-08-22 · 逐组件核对 33 个装修组件 + 内容管理全链路

结论：组件数量够了，缺的是"表现力"——样式系统只有 6 个可调项，页面结构只能一维平铺

33 个组件在后台和小程序端双端都已实现（MINIAPP_RENDER_SUPPORTED_TYPES 与实际 wxml 分支完全对齐，还有发布前拦截，这块做得比多数同类系统扎实）。所以问题不在"组件少"。

真正的天花板有两个。第一，组件的样式只能调 6 项：四向外边距、圆角、卡片间距、文字色、字号、显隐——没有背景色、没有背景图、没有内边距、没有阴影、没有边框、没有对齐、没有动效。更关键的是 ComponentStyle 类型里明明声明了 padding_* 和 background_color，但小程序端 utils/render.js 的 parseStyle 里有一个 SKIP_SHELL_KEYS 集合，把它们主动丢弃了（注释写着"外壳不再吃白底/内边距/圆角，避免整块外框"）。这是一个为了修某个视觉 bug 而做的全局阉割，代价是整套背景与留白能力都没了。

第二，DSL 没有 children：ComponentInstance 只有 id / type / props / style，组件之间是平级数组。这意味着永远做不出左右分栏、卡片容器、Tab 切换区、吸顶锚点导航、通栏背景区块——而这些恰恰是"页面看起来丰富"的主要来源。

下面分四部分：架构级瓶颈 → 逐组件清单 → 建议新增组件 → 内容模块。每条都标了代码位置。

一、搭建器的四个架构级瓶颈

这四条不解决，逐个组件加 props 的收益会被结构限制吃掉大半。建议先做 B1 和 B2。

B1样式系统只有 6 个可调项，背景与内边距在渲染端被主动丢弃

属性面板「样式」页签的全部内容：margin_top/bottom/left/right（含四向联动锁）、border_radius、item_gap、text_color、font_size、visible。PropsPanel.vue 里没有第七个样式控件。

而 miniapp/utils/render.js:125 的 SKIP_SHELL_KEYS 明确跳过 background_color / padding_* / border_radius。dsl-renderer.js 里还有十几处 delete shellStyle.border_radius / delete shellStyle.background_color 的手工补丁——说明这套样式传导机制已经打了很多补丁，是时候重做而不是继续补。

建议：重建一层「组件外观」模型，明确区分外壳（margin、背景、圆角、阴影、边框）与内容区（padding、对齐、字体）。外壳背景支持：纯色 / 渐变（起止色+角度）/ 图片（含平铺、定位、蒙层透明度）。这一步做完，同样 33 个组件能搭出来的视觉效果会有量级差异——因为大部分"高级感"来自背景分区和留白节奏，而不是组件本身。

B2DSL 无嵌套，页面只能一维堆叠

types/page.ts:253 的 ComponentInstance 没有 children 字段，CanvasArea.vue 也不处理嵌套。所以现在的页面本质是"组件从上往下排队"。

做不出来的效果包括：左右两列（左图右文卡片组）、九宫格金刚区外的自由栅格、Tab 分组区（一个区域内切换"推荐/最新/热门"）、横向滑动卡片组、通栏背景包住若干组件、吸顶锚点导航、折叠展开区。

建议：引入一个 container 组件类型，props 含 layout: row|grid|tabs|scroll-x|collapse、列数、间距、背景，children 放子组件。DSL 升 schema_version: 2.0，渲染端做递归渲染（小程序端可用模板递归或限制两层嵌套以避免性能问题）。这是本清单里对"页面丰富度"影响最大的一条。

B3样式配置分裂在 props 与 style 两处，字段命名各自为政

同一件事有三套写法：分区标题把内边距和颜色写进 props（padding_top / title_color / subtitle_color / more_color），品牌顶栏也在 props 里（background_color / gradient_from / gradient_to / bar_padding_left），而通用样式又在 style 里。字号字段则有 font_size、title_font_size、subtitle_font_size、section_title_font_size、stat_value_font_size、benefit_font_size 等至少 8 种命名。

后果：运营调样式要在两个页签之间来回找；开发新增组件时不知道该往哪放；将来做"全局主题"时无法统一改写。

建议：定一条规则——凡是"长什么样"进 style，凡是"显示什么"进 props，字号统一为 style.typography.{title,subtitle,body}.size 结构。旧数据写一个迁移函数在读取时归一化，不必改历史 DSL。

B4没有区块复用，actions 是死字段

搭好的一组组件不能保存成"区块"复用，也不能跨页复制（editor.vue 里无相关能力）。运营做第二个活动页只能从零再拖一遍。

ComponentInstance.actions?: ComponentAction[] 在类型里声明了，但全项目没有任何地方读它——交互行为目前散在各组件的 link_type / link_url / action_type 里，五六种写法。

建议：① 支持多选组件「存为区块」进模板库，跨页/跨小程序复用；② 统一 actions 模型（跳页 / 打开 webview / 拨电话 / 打开小程序 / 复制 / 客服 / 分享 / 弹层），让所有组件共用一个"点击行为"配置器，顺便解决现在轮播图和图片各写一套 link 的问题。

四、内容管理模块

内容模块的编辑侧有三个"填了没用"的功能，展示侧有一个天花板。这几条都可验证。

编辑侧

C1SEO 标题与描述填了会被静默丢弃

content/edit.vue 有完整的「SEO 与分享配置」页签，提交时带上 seoTitle / seoDescription。但后端全项目搜不到这两个字段，mp_content 表也没有对应列——运营认真填的内容，保存后消失。

建议：要么补字段（并接入分享卡片标题、小程序页面 share_title），要么把这个页签去掉。静默丢数据比没有功能更糟。

C2「定时发布」到点不会发

编辑页有发布方式：立即发布 / 定时发布 / 存为草稿，选定时还能选具体时间。但后端没有任何 @Scheduled 任务（上一份检查报告 P1-8 已确认），也没有发布调度逻辑。运营设了明早 9 点发布，到点内容还是草稿。

建议：补一个每分钟扫描的发布任务；同时在列表页给"待发布"内容一个明确的状态标识和倒计时。

C3富文本编辑器基于已废弃的 execCommand，缺块级排版能力

PageRichTextEditor.vue（906 行）是手写的 contenteditable，全部依赖 document.execCommand——这个 API 已被各浏览器标记为 deprecated，行为在不同浏览器下不一致，未来有失效风险。

现有能力：粗斜体下划线删除线、H1~H3、文字色/背景色（含吸管）、字号、三种对齐、缩进、有序无序列表、链接、图片（可设 100%/75%/50%/自定义宽度）、清除格式。

缺的都是"让内容好看"的部分：引用块、代码块、高亮提示框（信息/警告/要点三色卡）、分割线、表格、图注（图片下方小字说明）、多图并排、折叠区、行间距与首行缩进、字间距、视频嵌入、锚点目录。

建议：换成基于 ProseMirror 的编辑器（TipTap）或 wangEditor 5，两者都支持自定义节点——这样才能实现下面 C4 说的"内嵌商品卡"。同时补两个国内内容工具的标配：一键排版（统一字号行距、段间距、首行缩进、清理空段）和公众号粘贴清洗（粘进来的富文本自动剥离 section 嵌套与内联样式，现在这件事是靠 article-content.js 里近 200 行正则在后期补救的）。

C4内容形态做了一半：video 能识别不能创建，也没有渲染

V37 迁移里 content_type 的注释是 article=长文 note=笔记 video=视频 data=数据，小程序 content-detail.js 也有 video / data 的形态判断分支。但：后台编辑器只提供 长文 / 笔记 / 动态 三种（moment 还不在 V37 的注释里），而详情页 wxml 里连一个 <video> 标签都没有——选了视频形态也放不出视频。

建议：先把形态定义统一（建议 article / note / moment / video 四种，去掉 data 或明确它的形态），再补视频形态的编辑（视频源+封面+时长）与详情页渲染。视频内容是当前最有效的内容形式，值得补齐。

C5内容运营缺少几个高频动作

· 置顶与推荐位：只有 sort_order，没有"首页推荐""频道置顶"这类位置标记，运营只能靠调排序值猜。

· 批量操作：批量改分类、批量打标签、批量上下线。

· 版本与草稿：页面有版本管理，内容没有——改坏了无法回滚。

· 内容模板：常用结构（活动通知、产品说明、案例分享）存成模板，新建时套用。

· 敏感词与合规校验：发布前扫描违禁词（微信审核对医疗、金融、绝对化用语很敏感），现在完全没有。

展示侧

C6点赞、收藏、评论、关注全部是本地假态

content-detail.js 里 onLikeTap / onFavoriteTap / onSubmitComment / 关注，全部只写 StorageUtil 本地缓存，一个接口都没调。后端 MpContentController 也确实只有两个 GET 接口。

后果：换台手机全没了；后台看不到任何互动数据；用户 A 的评论用户 B 永远看不到。UI 上却做得很完整（评论抽屉、点赞动效、评论数展示），用户会当真。

建议：这是"看起来有社区，实际没有社区"。补三张表（点赞/收藏/评论）+ 对应接口，评论要带审核开关（内容安全是小程序审核重点）。如果短期不做，建议先把评论入口隐藏——留着比去掉伤害更大。

C7正文用原生 rich-text 渲染，样式与交互都被卡死

content-detail.wxml:184：<rich-text nodes="{{article.content}}">。微信原生 rich-text 的限制很硬：图片不能点击预览、不能长按识别、不支持懒加载、不支持 video/audio、不响应任何事件、部分标签与样式被过滤。

这直接意味着：公众号文章搬过来后，用户点图片没反应（这是最被投诉的一点）；文章里的视频显示不出来；无法在正文中插入可点击的商品卡。

建议：换成 mp-html 这类富文本渲染组件（开源、微信生态通用），一次性获得图片预览与懒加载、视频播放、表格、代码块、自定义标签、锚点跳转、内容内嵌小程序组件的能力。这是内容模块投产比最高的单点改造，工作量约 1~2 天。

C8正文里挂不了商品，内容与交易之间没有桥

接上 C7 的 mp-html 后，可以支持自定义标签 <product id="123"/>，编辑器里插入商品卡、正文中原位渲染、点击直达详情页，订单记录来源内容 ID。这是把已有的公众号内容同步投入变现的关键一步（上一份建议 F3 讲的是数据模型，这里是渲染实现）。

五、内容样式体系：从"逐条调字号"到"套排版模板"

S1正文排版主题

目前每篇文章的观感取决于编辑当时手调的字号和颜色，同一个小程序里的文章风格各不相同。建议提供 4~6 套正文排版主题（标准阅读 / 杂志风 / 极简 / 大字号适老 / 深色），主题定义标题层级、正文字号行距、段间距、引用块与图注样式、配图圆角。编辑只选主题，不调具体值。

S2页面主题令牌

页面级配置现在只有 background_color 和分享标题图（PageConfig 共 7 个字段），全局配置只有下拉刷新和触底加载两项。建议加一层页面主题：主色、辅助色、圆角档位、卡片阴影档位、字体规模、背景（色/渐变/图）。组件默认继承主题，个别覆盖。换一次主题，整个小程序换肤——这是同类产品拉开差距的能力，也是多客户复用模板的前提。

S3内容卡片样式库

文章/笔记/动态在列表中的卡片样式目前是写死的。建议每种内容形态提供 3~4 种卡片样式（大图/左图右文/纯文/瀑布流/横滑），由组件的 style_type 统一选择，与 S2 的主题联动。这样同一批内容在首页、频道页、专题页能呈现不同观感。

六、实施顺序

  1. 第一步（约 1 周，收益最直接）：C7 换 mp-html 渲染器（解锁图片预览与视频）+ C1 SEO 字段落库或下线 + C2 定时发布调度 + C6 互动接口（或先隐藏入口）。这四条都是"用户已经能看到但实际不工作"的问题，优先级高于任何新功能。
  2. 第二步（约 2 周，解锁表现力）：B1 重建外观模型（背景/内边距/阴影/边框/渐变）——这一步做完，现有 33 个组件的搭建效果会立刻上一个台阶，且不需要新增任何组件。
  3. 第三步（约 2~3 周，结构升级）：B2 容器组件 + DSL v2 递归渲染，配套新增图片热区、通栏背景块、卡片组、锚点导航四个组件。到这一步，搭建器才真正具备做"专题页"的能力。
  4. 第四步（持续）：B3 字段归一 + B4 区块复用与统一 actions；C3 换编辑器并补块级排版；S1~S3 主题体系；逐组件按第二部分的清单补齐 props。
