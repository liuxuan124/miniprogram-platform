一、本轮发现

Y1黑名单只覆盖登出，禁用账号和改密后旧 token 仍然可用

JwtBlacklistService 写得很干净（Redis 存 token 的 SHA-256，TTL 按剩余有效期），但全项目只有一处调用：AuthServiceImpl:193 的 logout。

于是这两条路径仍然漏：改密码（changePassword 只更新 passwordHash，不吊销已签发的 token）；禁用管理员（JwtAuthenticationFilter.buildAuthorities 读 AdminUser 只为取角色，不判断 status）。所以员工离职被禁用后，他手上的 token 在有效期内（最长 24 小时）照样能操作后台。

建议：① 改密时把当前 token 加入黑名单并要求重新登录；② 过滤器里加一句 if (adminUser.getStatus() == 0) → 401——这一句成本最低、收益最大；③ 禁用账号时可顺带按 userId 打一个"签发时间早于此刻的一律失效"的标记。

Y2日统计的活跃用户去重是在内存里做的

StatisticsDailyJob 里：

pageAccessLogMapper.selectList(...当日全部记录...)
    .stream().map(PageAccessLog::getUserId).distinct().count();

把当天所有页面访问日志全量拉进 JVM 再去重。日活几千时无所谓，但这张表是增长最快的表之一，加上任务每小时还跑一次今日快照，量上来后会明显变慢甚至 OOM（后端堆只有 512M）。订单那段也是全量拉取再求和，风险小一些。

建议：PageAccessLogMapper 里已经有现成的 COUNT(DISTINCT user_id) 写法（第 20、32 行），补一个按日期的 count 方法直接用即可；订单同理改成 SELECT COUNT(*), SUM(pay_amount)。顺带给 mp_page_access_log 和 mp_analytics_event 定个保留期（比如 90 天）和清理任务。

Y3三条收尾建议

· 黑名单在 Redis 故障时是 fail-open（isBlacklisted 异常返回 false 放行）。这是合理取舍——Redis 挂了不至于全站登录失效——但要知道：Redis 不可用期间吊销是失效的。建议在监控里给 Redis 加告警。

· CI 没有组件白名单一致性检查。迁移排序检查加得很好，但"后台注册表 / 小程序 wxml / 后端发布校验"三处一致才是历史上真正漂移过的地方（当初就是它卡住了发布）。建议照着迁移那个 job 的写法再加一个，十几行脚本。

· 装修器富文本组件仍是原生 rich-text，只是加了个"查看图片 (N)"的按钮兜底——务实，但不是原位点击预览。商品详情、活动详情、问答详情三个页面同理。什么时候有空可以统一换 mp-html。
