# 活动报名自动审核 + 个人签到二维码设计

日期：2026-08-13  
状态：已实现  
范围：小程序活动报名（微信身份 + 手机短信验证自动通过）、每人独立签到二维码、后台扫码核销

## 1. 目标

- 小程序用户**均已微信登录**；报名时后台记录其微信身份信息。
- 报名须填写手机号并完成**短信验证码**校验；校验通过即**自动审核通过**（本期不做复杂人工审核规则引擎）。
- 审核通过后为**每人**生成随机唯一签到码，小程序出示**二维码**；工作人员扫用户码核销。
- 替换当前「整场活动共用一串 CHK-xxx 文字码」的前端假实现。

## 2. 已确认决策

| 项 | 结论 |
|----|------|
| 核销方式 | 用户出示个人二维码 → 工作人员扫码核销 |
| 签到码生效 | 仅 `approved` 后生成/可出示 |
| 审核策略 | 全部自动审核（短信验证通过即通过） |
| 身份前提 | 小程序端必须已微信登录；记录 openid 等微信信息 |
| 手机 | 必填 + 短信验证码；对上才通过 |
| 不做（本期） | 未登录游客报名；复杂自动/人工条件引擎；活动级共用签到码 |

管理员仍可在「管理报名」中**手动拒绝/作废**已通过记录（兜底），但不作为主流程。

## 3. 业务流程

```text
用户(已登录) 打开活动详情
  → 填写姓名、手机号（及场次等）
  → 获取短信验证码 → 提交报名(含验证码)
  → 服务端：校验登录态 + 绑定 user/openid + 校验短信
  → 写入 signup.status = approved
  → 生成唯一 check_in_code，关联 signup / check_in 记录
  → 小程序展示「报名成功」+ 可进入「我的签到码」二维码页

现场：
  工作人员打开后台「签到核销」→ 扫用户二维码
  → 服务端校验 token 有效、未核销、活动匹配
  → status = VERIFIED，记录核销人/时间
```

## 4. 数据模型

### 4.1 报名 `mp_activity_signup`（增量）

| 字段 | 说明 |
|------|------|
| `user_id` | 必填（微信登录用户） |
| `name` / `phone` / `session` | 现有 |
| `status` | `pending` / `approved` / `rejected`；主路径直接 `approved` |
| `check_in_code` | 新增：通过后写入，唯一随机串（建议 ≥32 字符或 UUID） |
| `check_in_status` | 新增：`none` / `pending` / `verified`（或复用 check_in 表） |
| `approved_at` | 新增：自动通过时间 |
| `rejected_reason` | 可选：人工拒绝原因 |

唯一约束：`check_in_code` UNIQUE；建议 `(activity_id, user_id)` 唯一防重复报名（若产品允许同活动多次报名则另议，**默认一人一场**）。

### 4.2 签到 `mp_activity_check_in`

已有 `check_in_code`、`status(PENDING/VERIFIED)`、`verify_method`、`verified_by`。

约定：

- 报名通过时创建一条 `PENDING` 记录（或首次出示时惰性创建，**推荐报名通过时创建**，便于统计）。
- 二维码载荷：建议 `{"t":"activity_checkin","c":"<check_in_code>"}` 或短链 token，避免明文可猜。
- 核销：`SCAN`，`status=VERIFIED`，写 `check_in_time` / `verified_by`。

### 4.3 用户微信信息

沿用现有 `User` / 小程序用户：`openid`、昵称、头像等；报名接口强制登录，落库 `user_id`，列表/导出可展示微信昵称 + openid 摘要。

### 4.4 短信验证

- 系统配置组已有 `sms` 相关密钥项；补齐「发送验证码 / 校验验证码」服务（手机号 + 场景码如 `activity_signup`）。
- 频控：同一手机号发送间隔、日上限；验证码 TTL（如 5 分钟）；校验成功一次性消费。
- 未配置短信通道时：开发环境可开关 mock（仅本地），生产必须真实短信。

## 5. 接口（概要）

### 小程序

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/v1/mp/sms/send` | 发送验证码（需登录；body: phone, scene） |
| POST | `/api/v1/mp/activities/{id}/signup` | 报名：name, phone, session?, smsCode；成功返回 signup + checkInCode 摘要 |
| GET | `/api/v1/mp/activities/{id}/my-signup` | 我的报名状态 + 是否可展示签到码 |
| GET | `/api/v1/mp/check-ins/qr` | 当前用户某活动签到码（仅 approved 且未核销或按产品允许重复展示） |

### 管理端

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/v1/admin/activity-check-ins/scan` | body: code 或扫码原文 → 核销结果（姓名、手机、活动名） |
| GET | 现有报名列表 / 核销统计 | 展示每人签到状态、微信信息；去掉「整场 CHK 文字码」生成 |

后台 UI：

- 「签到码」入口改为「扫码核销」（摄像头或扫码枪输入）。
- 「管理报名」：状态、签到状态、微信昵称；支持人工拒绝。
- 核销记录列表沿用并强化按活动筛选。

## 6. 小程序 UI

- 报名表单：姓名、手机、获取验证码、提交（登录态拦截）。
- 报名成功页 / 活动详情已报名态：展示个人签到二维码 + 文字码备份 +「已核销」态。
- 二维码不可在 `rejected` / 未通过时展示。

## 7. 安全与规则

- `check_in_code` 高熵、不可枚举；接口不按活动公开列表码。
- 已核销码再次扫描：明确提示「已核销」，不重复计。
- 跨活动码：拒绝并提示活动不匹配（若扫码上下文带 activityId）。
- 名额：通过时占用名额；拒绝/取消时释放（与现有 `signed` 计数对齐）。

## 8. 非目标（本期明确不做）

- 未微信登录的游客报名路径。
- 可配置规则引擎（会员自动过、满员策略等）。
- 工作人员端独立小程序（可用管理后台 H5 扫码即可）。
- 改签/转让签到码。

## 9. 验收标准

1. 已登录用户填手机并短信校验成功 → 报名 `approved`，后台可见微信信息 + 手机号。
2. 短信错误/过期 → 不能通过。
3. 通过后用户可见个人二维码；未通过不可见。
4. 后台扫码成功核销一次；重复扫提示已核销。
5. 活动列表不再依赖前端拼装的共用 `CHK-xxx` 作为正式签到手段。
