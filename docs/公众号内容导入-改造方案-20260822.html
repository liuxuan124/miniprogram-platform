公众号内容导入：改造方案

交付给开发执行 · 2026-08-22 · 目标：把全量导入从「同步阻塞 + 前端超时」改为「异步任务 + 进度可见」

一句话：功能是好的，问题只在于它跑得比前端等得久

公众号导入的两条链路（API 全量同步 和 链接批量导入）已经实现且逻辑完整——分页拉到底、长文与贴图分别入库、正文图片自动转存、按 external_id 去重可重复跑。不需要重写。

唯一的硬伤是它是同步阻塞的：一次请求里要拉列表、逐篇取详情、下载并转存每一张图片。而前端 axios 的超时是 15 秒（admin/src/api/request.ts:26）。几十篇内容以上必然超时报错，但后端其实还在跑——运营看到"失败"会重复点击，反而造成并发拉取、更慢，还容易撞微信的接口配额。

本方案把它改成提交即返回任务号 + 前端轮询进度。后端核心导入逻辑基本不动，只在主循环里加进度上报。工作量约 1.5 人天。

二、方案总览

[运营点击导入]
   ↓ POST /sync-published            → 立即返回 { taskId }
   ↓ 后台线程开始跑（原有导入逻辑不变，加进度上报）
   ↓ 进度写入 Redis: wechat:import:{taskId}
[前端每 2 秒]
   ↓ GET /import-tasks/{taskId}      → { status, processed, total, result }
   ↓ status=running → 更新进度条
   ↓ status=success/failed → 停止轮询，展示结果，刷新内容列表

三条设计约束，请开发遵守：

  • 同一时间只允许一个导入任务（Redis 全局锁）。微信接口有调用配额，并发拉取只会更糟。重复提交时直接返回正在跑的那个 taskId，而不是报错。
  • 进度信息放 Redis，不建表。这是过程数据，TTL 24 小时即可，项目里 PreviewDraftServiceImpl 已有同款写法可参考。
  • 不动 upsertPublishedItem 及其以下的任何导入逻辑。这次只做"包一层异步 + 报进度"。

三、后端改动

B1　新增异步线程池配置

新增 backend/src/main/java/com/miniprogram/config/AsyncConfig.java

@Configuration
@EnableAsync
public class AsyncConfig {
    @Bean("importExecutor")
    public ThreadPoolTaskExecutor importExecutor() {
        ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(1);          // 串行执行，避免并发打微信接口
        ex.setMaxPoolSize(1);
        ex.setQueueCapacity(5);
        ex.setThreadNamePrefix("import-");
        ex.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy());
        ex.initialize();
        return ex;
    }
}

注意：核心线程数设 1 是刻意的。这类任务不需要并发，串行反而稳定。

B2　新增任务状态服务

新增 service/ImportTaskService.java + service/impl/ImportTaskServiceImpl.java

Redis 键设计：

键值TTL用途
wechat:import:{taskId}任务 JSON（见下）24 小时任务状态与进度
wechat:import:running当前 taskId2 小时全局互斥锁，SETNX

任务 JSON 结构（前后端契约，字段名请勿改）：

{
  "taskId": "a1b2c3d4",
  "type": "sync",              // sync = API 全量同步；url = 链接导入
  "status": "running",         // pending | running | success | failed
  "total": 187,                // 待处理条目总数；拉到列表前为 0
  "processed": 32,             // 已处理条目数
  "currentTitle": "跨境电商合规指南",   // 当前处理的标题，前端展示用
  "startedAt": "2026-08-22T14:03:11",
  "finishedAt": null,
  "operatorId": 1,
  "error": null,               // status=failed 时的错误摘要
  "result": null               // 完成时放 WeChatContentSyncResultVO 原样
}

需要的方法：String tryStart(String type, Long operatorId)（拿不到锁返回已有 taskId）、void updateProgress(String taskId, int processed, int total, String currentTitle)、void finish(String taskId, WeChatContentSyncResultVO result)、void fail(String taskId, String error)、TaskVO get(String taskId)、TaskVO getRunning()。

务必：finish 和 fail 里都要释放 wechat:import:running 锁，且放在 finally 中——否则一次异常会让导入功能锁死到 TTL 过期。

B3　改造导入服务

修改 service/WeChatOfficialAccountContentSyncService.java，加两个异步方法（保留原同步方法不动，内部复用）：

@Async("importExecutor")
void syncAllPublishedAsync(WeChatContentSyncRequestDTO request, String taskId);

@Async("importExecutor")
void importFromUrlsAsync(WeChatUrlImportRequestDTO request, String taskId);

修改 WeChatOfficialAccountContentSyncServiceImpl：

  1. 给 syncAllPublished 加一个重载 syncAllPublished(request, taskId)，taskId 为 null 时行为与现在完全一致。
  2. 在 listAllPublishedRecords() 返回之后（约 81 行），先算出待处理条目总数并写一次进度：importTaskService.updateProgress(taskId, 0, records.size(), null)。
    注：总数用发布记录数即可，不必精确到图文条目数——多图文会让 processed 超过 total，前端按 Math.min 处理即可；或者在内层循环前把 total 修正为累计条目数，二选一，实现时说明清楚。
  3. 内层 for 每处理完一条（约 122 行 switch 之后），调一次 updateProgress(taskId, articlesProcessed, total, item.getStr("title"))。注意节流：每条都写 Redis 没问题（一次写入不到 1ms），但如果担心，可以每 5 条写一次。
  4. 异步方法体：try 调用带 taskId 的同步方法 → finish(taskId, result)；catch → fail(taskId, e.getMessage())。异步方法内必须自己兜住所有异常，@Async 方法抛出的异常不会传播给调用方。
  5. 链接导入 importFromUrls 同样处理：total = urls.size()，每条抓完报一次进度。

B4　改造 Controller

修改 controller/WeChatOfficialAccountController.java：

@PostMapping("/sync-published")
@PreAuthorize("hasAuthority('content:update')")
public R<ImportTaskVO> syncPublished(@RequestBody(required = false) WeChatContentSyncRequestDTO request) {
    String taskId = importTaskService.tryStart("sync", SecurityUtils.getCurrentUserId());
    ImportTaskVO existing = importTaskService.get(taskId);
    if ("running".equals(existing.getStatus()) && !existing.isJustCreated()) {
        return R.ok("已有导入任务正在执行，返回该任务进度", existing);   // 不报错，直接给回正在跑的任务
    }
    contentSyncService.syncAllPublishedAsync(request, taskId);
    return R.ok(existing);
}

@GetMapping("/import-tasks/{taskId}")
@PreAuthorize("hasAuthority('content:list')")
public R<ImportTaskVO> getTask(@PathVariable String taskId) { ... }

@GetMapping("/import-tasks/running")
@PreAuthorize("hasAuthority('content:list')")
public R<ImportTaskVO> getRunning() { ... }   // 前端打开弹窗时恢复进度用

/import-urls 同样改为返回 taskId。

参数校验（分类是否存在、URL 是否合法、条数上限 10）要放在 tryStart 之前同步做完，参数错误就直接报错，不要先建任务再失败。

四、前端改动

F1admin/src/api/wechat.ts

新增类型与方法：

export interface ImportTask {
  taskId: string
  type: 'sync' | 'url'
  status: 'pending' | 'running' | 'success' | 'failed'
  total: number
  processed: number
  currentTitle?: string
  error?: string
  result?: WeChatContentSyncResult
}
export function getImportTask(taskId: string) { return get<ImportTask>(`${BASE_URL}/import-tasks/${taskId}`) }
export function getRunningImportTask() { return get<ImportTask>(`${BASE_URL}/import-tasks/running`) }

原有两个提交方法的返回类型改为 ImportTask。

F2admin/src/views/content/index.vue

改造 handleWeChatSyncImport()（803 行）与链接导入那个函数：

  • 提交后拿到 taskId，存进 ref，启动 setInterval 每 2 秒轮询一次。
  • 弹窗里用 <el-progress> 显示 processed / total，下方一行小字显示 currentTitle（"正在处理：xxx"）。
  • status 变为 success/failed 时：清除定时器、展示原来那套结果面板（message + failures 列表）、调 fetchList() 刷新列表。
  • 组件卸载与弹窗关闭时必须 clearInterval（onBeforeUnmount + 弹窗 close 事件），否则切页面后定时器泄漏。
  • 任务进行中：提交按钮置灰并显示"导入中…"；允许关闭弹窗，并提示"任务在后台继续，可稍后回来查看"。
  • 打开弹窗时先调一次 getRunningImportTask()，如果有正在跑的任务就直接进入进度态——这样刷新页面/换台电脑也能看到进度。
  • 轮询容错：单次请求失败不要立刻停，连续失败 3 次再停并提示。

F3不要用调大 timeout 的方式绕过

有人可能会想直接把 api/request.ts 的 timeout: 15000 改成 10 分钟——不要这么做。那会让所有接口都失去超时保护，真出问题时页面会一直转圈。如果一定要临时救急，只在这两个导入请求上单独传 { timeout: 600000 }，但正式方案还是走异步。

五、边界与异常清单

场景期望行为
重复点击提交返回正在跑的 taskId，前端直接进入进度态，不新建任务
导入中刷新页面/关闭弹窗任务继续；重新打开弹窗通过 /import-tasks/running 恢复进度
后端重启任务中断，Redis 里状态仍是 running。需在任务服务里加判断：startedAt 超过 2 小时仍是 running 视为失效，允许重新发起
Redis 不可用降级为原同步逻辑（直接执行并返回结果），不能因为 Redis 挂了就不能导入
单篇图文失败已有逻辑：计入 failed + failures，继续跑下一篇。保持不变
微信配额耗尽 / token 失效整个任务失败，error 里带上微信返回的 errcode，前端原样展示（40164=IP 白名单，45009=配额）
任务锁未释放锁 TTL 2 小时兜底；同时提供一个手动清理入口或直接删 Redis 键的运维说明

六、验收标准

  • 点击导入后 1 秒内返回，弹窗出现进度条，不再出现 15 秒超时报错
  • 进度条数字随处理推进，能看到当前正在处理的标题
  • 导入过程中关闭弹窗再打开，进度能恢复
  • 导入过程中再次点击提交，不会启动第二个任务
  • 完成后自动刷新内容列表，结果面板显示新建/更新/失败数量与失败明细
  • 用一个不存在的分类 ID 提交，立即报参数错误，且不占用任务锁
  • 把 Redis 停掉后提交，仍能完成导入（走降级同步路径）
  • 连续两次全量导入，第二次结果里 created=0、updated=N（验证去重仍然生效）

七、工作量与顺序

  1. 后端 B1+B2（线程池 + 任务服务）：约 3 小时
  2. 后端 B3+B4（导入服务加进度 + Controller）：约 3 小时
  3. 前端 F1+F2（API + 弹窗进度轮询）：约 4 小时
  4. 联调与验收：约 2 小时

合计约 1.5 人天。建议先做后端并用 Swagger/Postman 验通，再接前端。

八、本次不做的事

  • 不做任务历史列表——只保留"当前/最近一个任务"，够用。将来真需要再建表。
  • 不做断点续传——导入本身幂等，失败重跑一遍即可，续传的复杂度不值得。
  • 不做并发导入——串行是刻意的设计。
  • 不改动导入的解析逻辑（长文/贴图识别、图片转存、去重）——那部分现在是对的。

附录：给运营的导入操作说明

前置配置只需做一次

① 后台 系统设置 → 微信小程序配置 → 公众号配置，填公众号的 AppID 与 AppSecret（留空会退回用小程序凭证，通常不对）。

② 微信公众平台 → 开发 → 基本配置 → IP 白名单，加入服务器公网 IP，否则报 errcode 40164。

③ 接口权限要求已认证的服务号/订阅号；未认证账号只能用"链接导入"。

导入步骤建议顺序

  1. 先用链接导入试 1~2 篇，确认图片正常转存显示（验证链路通）
  2. 全量导入：同步范围选「只要长文」，导入状态选「存为草稿」
  3. 再跑一次：同步范围选「只要贴图」，同样存为草稿
  4. 内容列表按"导入时间"倒序检查，重点看图片与排版
  5. 确认无误后批量发布；API 没拉到的历史文章用链接导入补（单次 10 条以内）

说明：导入按 external_id 去重，重复跑是安全的，已存在的条目会更新而不是新建。正文图片会自动下载转存到自己的服务器（公众号图片有防盗链，不能直接外链）。

本方案基于 2026-08-22 的代码实况撰写，所有文件路径与行号可直接定位。核心导入逻辑（upsertPublishedItem 及以下）不在本次改动范围内。
