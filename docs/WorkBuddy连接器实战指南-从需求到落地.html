〇需求起点：先判断该不该做

0.1 原始诉求与真实痛点

诉求只有一句话：让 WorkBuddy 能连接自有后台，读取内容和资料，也能发布内容和资料。 翻译过来就是——把「登录后台 → 找到页面 → 手工改 → 点发布」这条链路，变成「跟 AI 说一句」。

在此之前，每次要看数据或改内容，只能 ssh 登生产 + curl 拼请求， 或让人肉进后台点。链路长、不可复用、无法被 AI 自主调用。

0.2 三条可选路线

把需求抽象成「把一个已有 HTTP 系统暴露给 AI 助手」，候选方案有三条，代价差别很大：

路线做法谁能用现实度
A 本地自建 MCP 写 Node/Python server，注册进 ~/.workbuddy/mcp.json，支持 url(HTTP) 与 command(stdio) 两种 仅本机 当天可跑，几十行起步
B 完整连接器插件 plugin.json + ai.workbuddy/cli.json + skills/，与官方连接器同构，带登录流程 可打包分发团队 能做，工作量约 ×3
C 上架官方市场 提交官方审核收录 全体用户 审核决定，不由己方控制
选 型 依 据 目标是内部系统、使用者只有自己、要求当天见效 → 选 A。 判断标准很简单：受众是自己还是别人。自用走 A，分发走 B，公开走 C。 本案例最终选 A，并把 B 里的 skills/ 思想单独抽出来用（见第八章）。

0.3 落地前先写清验收标准

避免"做到一半不知道什么叫完成"。本案例定下四条：

  • 握手通过：WorkBuddy 能拉起进程并拿到工具清单
  • 数据真实：至少 3 个读工具返回生产库的真实记录
  • 写有围栏：写工具默认关闭，开启后敏感模块仍不可达
  • 凭据不落地：密码不出现在对话、命令行、mcp.json 三处

这四条后面每一章都能对应上，也是最后验收的依据。

一摸清接口：不写一行代码先查清四件事

这一步最容易被跳过，却决定了后面所有代码能不能写对。 目标产物是一张 接口坐标表 —— 后面写工具层时，它是唯一依据。

1.1 找 Controller：确定路径前缀

从后端源码入手，按目录找控制器：

定位后端控制器
cd backend && find src/main/java -type d -name "controller"

# 逐个看路径前缀与接口清单
grep -nE "@(Get|Post|Put|Delete)Mapping|@RequestMapping" \
  src/main/java/com/miniprogram/controller/ContentController.java

本案例结论：管理端统一前缀 /api/v1/admin，统一响应壳 R{code, message, data}，成功码 200。

1.2 找鉴权规则：哪些路径要什么角色

安全配置类决定哪些接口能被哪个角色调用，直接决定了后面"该给连接器建什么权限的账号"：

本案例 SecurityConfig 关键规则
.authorizeHttpRequests(auth -> auth
    // 财务 / 退款 / 系统 / 账号 / 角色 / 权限 → 只有超管
    .requestMatchers("/api/v1/admin/finance/**", "/api/v1/admin/refunds/**",
                     "/api/v1/admin/system/**", "/api/v1/admin/admin-users/**",
                     "/api/v1/admin/roles/**", "/api/v1/admin/permissions/**")
        .hasRole("super_admin")
    .requestMatchers("/api/v1/admin/auth/login").permitAll()  // 登录免鉴权
    .anyRequest().authenticated()
)
这 条 规 则 埋 了 一 个 坑 上传接口 FileUploadController 的路径恰是 /api/v1/admin/system/upload， 落在 system 前缀下 → 非超管账号调上传必然 403。 这个坑在第七章、第十章还会出现，是"不查鉴权规则"的典型代价。

1.3 找 DTO：确定能传什么字段

写工具类时字段写错会静默失败，所以 DTO 要逐个看：

DTO 字段核对
grep -nE "private |class " src/main/java/com/miniprogram/dto/ContentDTO.java
grep -nE "private |class " src/main/java/com/miniprogram/dto/PageDraftDTO.java

两个关键发现，直接影响了工具设计：

  • PageDraftDTO 只有 dslContent + expectedVersion —— 存草稿只能传这两个
  • ContentDTO 没有 status 字段 —— 发布必须走独立的 /{id}/publish 接口，不能靠改字段

1.4 找登录与 JWT：确定认证方式

看 AuthController + JwtTokenProvider，确认三件事：登录接口是否免鉴权、返回什么、JWT 的 claims 规则。

1.5 产物：接口坐标表

把以上整理成一张表，后续写代码时不再回头翻源码：

资源方法与路径（前缀 /api/v1/admin）备注
内容列表 / 新建GET|POST /contents列表支持分页与筛选
内容详情 / 改 / 删GET|PUT|DELETE /contents/{id}PUT 需传全量字段
内容发布 / 下架PUT /contents/{id}/publish /unpublish发布是独立动作
页面列表 / 详情GET /pages GET /pages/{id}详情含 DSL 与版本号
页面存草稿 / 发布POST /pages/{id}/draft POST /pages/{id}/publish草稿 ≠ 线上
素材列表GET /assets返回 /uploads/... 相对路径
文件上传POST /system/upload⚠ 超管前缀
登录POST /auth/login免鉴权，返回 accessToken
错误码含义排查方向
110101用户名或密码错误用户名不存在，或 BCrypt 不匹配
110103账号已禁用账号 status 不为 1
200501用户名已存在映射到 HTTP 409
403角色无权访问该前缀核对 SecurityConfig 的 hasRole

二最小骨架：先跑通空壳，再逐个加能力

常见错误是"一口气写完 12 个工具再跑"，一旦握手失败，无法定位是传输问题、协议问题还是接口问题。 正确顺序：空壳 → 握手 → 加一个读工具 → 加认证 → 加写工具。

2.1 工程与依赖

package.json —— 只需一个依赖
{
  "name": "mcp-miniprogram",
  "version": "1.0.0",
  "private": true,
  "type": "module",          // ESM，与 SDK 一致
  "main": "src/index.js",
  "engines": { "node": ">=18" },
  "dependencies": { "@modelcontextprotocol/sdk": "^1.0.0" },
  "scripts": { "start": "node src/index.js" }
}
零 FRAMEWORK 传输用 stdio，HTTP 用 Node 原生 fetch，签名用原生 crypto，配置文件自己解析。 整个工程除 MCP SDK 外无任何三方依赖 —— 依赖越少，越不会在某次升级后突然跑不起来。

2.2 入口：只做三件事

MCP server 的入口极薄：读配置 → 建 Server → 连 stdio，只挂两个请求处理器。

src/index.js（骨架版）
import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { CallToolRequestSchema, ListToolsRequestSchema }
  from "@modelcontextprotocol/sdk/types.js";
import { loadConfig } from "./config.js";
import { visibleTools, callTool } from "./tools.js";

const cfg = loadConfig();   // 见第三章：刻意设计为「软失败」

const server = new Server(
  { name: "mcp-miniprogram", version: "1.0.0" },
  { capabilities: { tools: {} } }
);

// ① 告诉客户端「有哪些工具」
server.setRequestHandler(ListToolsRequestSchema, async () => ({ tools: visibleTools(cfg) }));

// ② 执行某个工具
server.setRequestHandler(CallToolRequestSchema, async (req) => {
  const { name, arguments: args } = req.params;
  return callTool(cfg, name, args || {});
});

async function main() {
  await server.connect(new StdioServerTransport());
  process.stderr.write(`[mcp-miniprogram] 已启动 · 工具数：${visibleTools(cfg).length}\n`);
}
main().catch((err) => {
  process.stderr.write(`启动失败：${err.stack || err.message}\n`);
  process.exit(1);
});
绝 对 不 要 用 console.log stdio 传输下 stdout 就是协议通道。任何 console.log 都会当成 JSON-RPC 消息发出去， 轻则客户端解析报错，重则握手直接失败。所有日志一律走 process.stderr.write。

2.3 冒烟客户端：每次改代码都能自查

写一个 48 行的小客户端，模拟 WorkBuddy 拉起进程并调用工具。 它的价值是：不必重启 WorkBuddy 就能验证改动。

scripts/smoke.js —— 握手 → 列工具 → 调一次
import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StdioClientTransport } from "@modelcontextprotocol/sdk/client/stdio.js";

const transport = new StdioClientTransport({
  command: process.execPath,
  args: ["src/index.js"],
  env: { ...process.env },      // 关键：把本机环境变量透传给子进程
});
const client = new Client({ name: "smoke-test", version: "1.0.0" }, { capabilities: {} });

await client.connect(transport);
console.log("✅ 连接成功（stdio 握手通过）");

const { tools } = await client.listTools();
console.log(`✅ 工具清单：${tools.length} 个`);
tools.forEach((t) => console.log(`   - ${t.name}`));

const toolName = process.argv[2];
if (toolName) {
  const res = await client.callTool({
    name: toolName,
    arguments: process.argv[3] ? JSON.parse(process.argv[3]) : {},
  });
  console.log(res.isError ? "❌ " + res.content?.[0]?.text
                        : "✅ " + res.content?.[0]?.text);
}
await client.close().catch(() => {});

三认证层：双模式与自动续期

认证是所有接口调用的前置。设计上给两条路，并按优先级自动选择： 有账号密码就走登录模式；有 JWT 密钥就走自签模式。

模式凭据适用场景特点
A 登录模式 MP_USERNAME + MP_PASSWORD 能拿到后台账号密码 不需要密钥，token 到期自动重登
B 自签模式 MP_JWT_SECRET 能拿到服务端 JWT 密钥（如生产 env） 零网络往返，但密钥泄露等于全库通行

3.1 登录模式：取 token 并提前续期

src/auth.js —— 登录与缓存
const state = { token: "", expireAt: 0, mode: "" };

async function login(cfg) {
  const res = await fetch(`${cfg.base}${ADMIN_API}/auth/login`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ username: cfg.username, password: cfg.password }),
    signal: AbortSignal.timeout(cfg.timeoutMs),   // 必须设超时，否则进程挂死
  });
  const json = await res.json().catch(() => null);
  if (!res.ok || !json || json.code !== 200 || !json.data?.accessToken) {
    throw new Error(
      `管理端登录失败：HTTP ${res.status} / code=${json?.code} / ${json?.message || "无返回"}`);
  }
  const ttlSec = Number(json.data.expiresIn || 7200);
  state.token    = json.data.accessToken;
  state.expireAt = Date.now() + ttlSec * 1000;
  state.mode     = "login";
  return state.token;
}

export async function getAccessToken(cfg) {
  if (!cfg.configured) throw new Error(`连接器未完成配置 · ${cfg.configError}`);
  if (cfg.username && cfg.password) {
    // 提前 5 分钟续期，避免临界点刚好过期
    if (!state.token || state.mode !== "login" || Date.now() > state.expireAt - 5 * 60 * 1000) {
      return login(cfg);
    }
    return state.token;
  }
  // 自签模式：现签，2h 有效期内复用
  if (!state.token || state.mode !== "self" || Date.now() > state.expireAt - 5 * 60 * 1000) {
    state.token = selfSignedToken(cfg);
    state.expireAt = Date.now() + 2 * 60 * 60 * 1000;
    state.mode = "self";
  }
  return state.token;
}

export function invalidateToken() {   // 401 后强制刷新
  state.token = ""; state.expireAt = 0; state.mode = "";
}

3.2 自签模式：claims 必须严格照抄服务端

自签不是随便签一个 JWT 就行 —— 服务端过滤器会校验 claims。 本案例 JwtAuthenticationFilter 要求：sub 不能以 wx_ 开头、 userId 对应的管理员必须存在且 status=1。 所以 claims 结构照抄 JwtTokenProvider：

自签 HS256
function selfSignedToken(cfg) {
  const now = Math.floor(Date.now() / 1000);
  return signJwt(cfg.jwtSecret, {
    sub: "admin",           // 不能以 wx_ 开头，否则被判为小程序端 token
    userId: cfg.adminUserId,   // 必须对应一个 status=1 的管理员
    typ: "access",
    iat: now,
    exp: now + 7200,
  });
}
配 置 软 失 败 —— 一个反直觉但必要的设计 第一版在"读不到凭据"时直接 process.exit(1)，结果：WorkBuddy 拉起进程后进程立刻死， 连接器面板显示成黄点 + 加载失败，既看不到工具，也不知道错在哪。 正确做法是照常启动、照常列出工具，把错误留到调用时给出明确指引： 
cfg.configured = Boolean(cfg.username && cfg.password) || Boolean(cfg.jwtSecret);
cfg.configError = cfg.configured ? "" : "未配置认证方式。请运行 scripts/setup-credentials.sh 生成凭据文件。";
// index.js 里即便 loadConfig 抛错，也兜底构造一个 configured:false 的 cfg 继续启动

四请求层：把所有出口收拢到一道闸

请求层是全工程唯一对外发请求的出口。把鉴权、黑名单、重试、错误翻译都放在这里， 好处是：任何工具都自动获得这些能力，新加工具时不可能绕过。

4.1 统一封装

src/api.js
export async function request(cfg, { method = "GET", path, query = {}, body = null, retry = true }) {
  assertPathAllowed(path);            // ① 出口闸：敏感路径拦截

  const url = new URL(`${cfg.base}${path}`);
  for (const [k, v] of Object.entries(query)) {
    if (v !== undefined && v !== null && v !== "") url.searchParams.set(k, String(v));
  }

  const headers = { Accept: "application/json" };
  if (body !== null) headers["Content-Type"] = "application/json";
  headers.Authorization = `Bearer ${await getAccessToken(cfg)}`;   // ② 自动带 token

  const res = await fetch(url, { method, headers,
    body: body === null ? undefined : JSON.stringify(body),
    signal: AbortSignal.timeout(cfg.timeoutMs) });

  if ((res.status === 401 || res.status === 403) && retry) {   // ③ 401 自动重登重试
    invalidateToken();
    return request(cfg, { method, path, query, body, retry: false });  // 只重试一次
  }

  const text = await res.text();
  let json = null;
  try { json = text ? JSON.parse(text) : null; }
  catch { throw new Error(`响应不是合法 JSON：HTTP ${res.status} ${text.slice(0, 200)}`); }

  if (!res.ok) throw new Error(`HTTP ${res.status} · code=${json?.code} · ${json?.message || ""}`);

  // ④ 关键：HTTP 200 但业务码非 200，同样是失败
  if (json && json.code !== undefined && json.code !== 200) {
    throw new Error(`业务失败 code=${json.code} · ${json.message || ""}`);
  }
  return json ? json.data : null;   // 只返回 data，剥掉响应壳
}

4.2 三个容易漏的点

业务码 ≠ HTTP 状态码
很多后台统一返回 HTTP 200，失败藏在 body.code 里。只判 res.ok 会把失败当成成功，AI 拿到空数据还以为成功了。
重试必须有终止条件
401 重试传 retry:false，否则会无限递归。这是"加了自动重试"后最常见的线上事故。
超时必须显式设置
MCP server 是长驻进程，一次 fetch 挂死会让整个连接器失去响应，且不会被自动回收。

4.3 上传走独立通道

文件上传是 multipart，不能走 JSON 通道，单独封装并复用同一道出口闸的例外规则：

src/api.js —— 上传
export async function uploadFile(cfg, filePath, field = "file") {
  const { readFile } = await import("node:fs/promises");
  const buf = await readFile(filePath);
  const form = new FormData();
  form.append(field, new Blob([buf]), filePath.split("/").pop());

  const res = await fetch(`${cfg.base}${ADMIN_API}/system/upload`, {
    method: "POST",
    headers: { Authorization: `Bearer ${await getAccessToken(cfg)}` },
    body: form,
    signal: AbortSignal.timeout(cfg.timeoutMs),
  });
  const json = await res.json().catch(() => null);
  if (!res.ok || !json || json.code !== 200) throw new Error(`上传失败：HTTP ${res.status}`);
  return json.data;
}

五工具层：声明与分发

工具层是 AI 与后台接口之间的契约。这里的设计要点是： description 不是写给人看的注释，而是写给 AI 看的提示词 —— 它决定 AI 会不会调、会不会传对参数。

5.1 声明三件套

src/tools.js —— 一条工具声明
{
  name: "mp_list_contents",
  description:
    "列出小程序后台的内容（文章/视频/图集等）。可按关键词、状态、类型、分类筛选，
     支持分页。返回标题、状态、类型、更新时间。",
  inputSchema: {
    type: "object",
    properties: {
      keyword:     { type: "string", description: "标题关键词" },
      status:      { type: "string",
                     description: "状态：draft 草稿 / published 已发布 / offline 已下架，不传查全部" },
      contentType: { type: "string", description: "内容类型，如 article / video / gallery" },
      categoryId:  { type: "number", description: "分类 ID" },
      current:     { type: "number", description: "页码，默认 1" },
      size:        { type: "number", description: "每页条数，默认 10，最大 100" },
    },
  },
}
写 DESCRIPTION 的 三 条 经 验 ① 枚举值要写全：写 status 不写 "draft/published/offline"，AI 只能瞎猜；
② 副作用要说清：如「存草稿不会改动线上版本，必须再调 mp_publish_page 才会生效」；
③ 约束要写进去：如「封面必须是 /uploads/... 相对路径」，否则 AI 会拼错域名。

5.2 分发：一个 switch 到底

src/tools.js —— 分发与先读后写
export async function callTool(cfg, name, args = {}) {
  try {
    if (cfg.readOnly && WRITE_TOOLS.has(name)) {   // 二次拦截，防绕过清单
      return fail(new Error(`当前为只读模式（MP_READ_ONLY=1），${name} 已禁用`));
    }
    switch (name) {
      case "mp_list_contents":
        return ok(await request(cfg, { path: C, query: args }));
      case "mp_get_content":
        return ok(await request(cfg, { path: `${C}/${args.id}` }));

      // 更新：先读再合并，避免未传字段被清空
      case "mp_update_content": {
        const { id, ...patch } = args;
        const current = await request(cfg, { path: `${C}/${id}` });
        return ok(await request(cfg, {
          method: "PUT", path: `${C}/${id}`, body: { ...current, ...patch } }));
      }

      case "mp_publish_content":
        return ok(await request(cfg, { method: "PUT", path: `${C}/${args.id}/publish` }));
      case "mp_save_page_draft":
        return ok(await request(cfg, { method: "POST",
          path: `${P}/${args.id}/draft`,
          body: { dslContent: args.dslContent, expectedVersion: args.expectedVersion } }));

      default: return fail(new Error(`未知工具：${name}`));
    }
  } catch (err) {
    return fail(err);   // 统一转成 isError 响应，不让异常冲垮进程
  }
}
片 段 更 新 要 先 读 后 写 后台的 PUT 通常是全量覆盖。若直接把 AI 传来的部分字段 PUT 上去， 未传的字段（封面、标签、图集）会被清空。 正确做法：先 GET 拿当前值，合并补丁后再 PUT。

5.3 命名与分组

工具名统一带前缀 mp_。原因是 WorkBuddy 会同时挂多个连接器（本例还有 zsxq）， 前缀能让 AI 一眼分清工具归属。写工具用 WRITE_TOOLS 集合显式登记， 只读模式下既从清单移除、又在调用时拒绝 —— 两道都要有，只靠隐藏清单拦不住直接点名调用。

六注册与启用：让 WorkBuddy 认领这个连接器

6.1 配置写法

~/.workbuddy/mcp.json
{
  "mcpServers": {
    "miniprogram": {
      "type": "stdio",
      "command": "/Users/lx/.workbuddy/binaries/node/versions/22.22.2-3/bin/node",
      "args": ["/Users/lx/项目文件/liuxuan/小程序搭建运营系统/tools/mcp-miniprogram/src/index.js"],

字段要点

staticEnv只放非秘密项。密码一律走凭据文件，见第七章

  1. 打开 WorkBuddy 连接器管理页
  2. 右上角「自定义连接器」入口 → 对 miniprogram 点信任
  3. 重启 WorkBuddy —— 已信任过的连接器改配置后必须重启才重载

6.3 面板显示"黄点 / 切换服务器状态失败"怎么查

黄点意味着进程没能正常握手。按顺序排查：

三步定位
# ① 手工拉起，看 stderr 是否输出「已启动」
echo '' | MP_READ_ONLY=1 node src/index.js

# ② 检查是否有残留进程占住
ps aux | grep mcp-miniprogram | grep -v grep

# ③ 用冒烟客户端复现 WorkBuddy 的完整握手
MP_READ_ONLY=1 node scripts/smoke.js

本案例实际踩到的是时序问题：先改了 mcp.json 指向凭据文件，凭据文件三分钟后才建好 —— 中间那次拉起因读不到凭据而 exit(1)，面板状态就此卡死。 这正是第三章「配置软失败」改造的由来。

七安全加固：三道闸与一条底线

这一章是整份文档最不该跳过的一章。连接器一旦可用，就等于给了 AI 一把能直接改生产库的钥匙。 设计目标不是"防止被攻破"，而是降低凭据泄露后的损失。

7.1 先认清三个暴露面

暴露面 ① 对话上下文
在对话里打出来的密码会进入会话历史与上下文，没有任何技术能撤回。这是最该避免的一条。
暴露面 ② 命令审计明文
WorkBuddy 的审计日志 ~/.workbuddy/audit-log/*.jsonl 中 commandPreview 字段完整保存命令原文，永久落盘。密码一旦出现在任何 shell 命令里就会被留存。
暴露面 ③ 配置明文
写进 mcp.json 的 staticEnv 是明文 JSON，容易被同步、截图、误提交。

7.2 闸一：凭据外置（密码不经对话、不经命令行）

做法：mcp.json 里只放路径，真凭据放在 600 权限的独立文件里； 写入靠交互式脚本，密码用 read -s 不回显，验证登录时由子进程直接读文件而非通过 shell 传参。

scripts/setup-credentials.sh —— 关键片段
# ① 密码不回显，且只回显长度供核对
read -r -s -p "后台密码（不回显）: " MP_PASSWORD; echo
echo "✓ 密码录入：${#MP_PASSWORD} 个字符"

# ② 写入 600 权限文件
{
  echo "MP_API_BASE=${MP_API_BASE}"
  echo "MP_USERNAME=${MP_USERNAME}"
  echo "MP_PASSWORD=${MP_PASSWORD}"
} > "${CRED_FILE}"
chmod 600 "${CRED_FILE}"

# ③ 当场验证登录：子进程读文件，密码不经命令行参数
"${NODE_BIN}" -e '...读取文件后 fetch /auth/login...' "${CRED_FILE}"
BEFORE
MP_PASSWORD 明文写在 mcp.json 的 staticEnv；密码通过对话告知；用 curl -u user:pass 测试（进审计日志）
AFTER
mcp.json 只含 MP_CREDENTIALS_FILE 路径；密码由所有者本人在终端 read -s 录入；验证由子进程读文件完成
配 套 的 解 析 器 凭据文件用自写的 30 行极简 dotenv 解析（支持 export 前缀、单双引号、# 行尾注释）， 并自动跳过 REPLACE_ME 之类占位值。不引三方库，也就不会出现"某个库升级后解析行为变了"的意外。

7.3 闸二：只读开关（默认关闭写能力）

MP_READ_ONLY=1 时，7 个写工具从清单里消失；即便被点名调用也会在 callTool 入口被拒。 两层都做，是因为"只隐藏清单"拦不住直接指定工具名的调用。

三重校验
# 只读模式 → 工具数应为 5
MP_READ_ONLY=1 node scripts/smoke.js
# ✅ 工具清单：5 个（只读模式）

# 关掉只读 → 工具数应为 12
MP_READ_ONLY=0 node scripts/smoke.js
# ✅ 工具清单：12 个

7.4 闸三：路径黑名单（敏感模块硬拦截）

即便以后有人往里加工具，也不该碰到财务、退款、账号、角色这类模块。 拦截点放在请求层入口 —— 所有请求必经，无法绕过。

src/config.js
const SENSITIVE_PREFIXES = [
  `${ADMIN_API}/finance`, `${ADMIN_API}/refunds`, `${ADMIN_API}/system`,
  `${ADMIN_API}/admin-users`, `${ADMIN_API}/roles`,
  `${ADMIN_API}/permissions`, `${ADMIN_API}/agent`,
];
const SENSITIVE_EXCEPTIONS = new Set([`${ADMIN_API}/system/upload`]);  // 素材上传是例外

export function assertPathAllowed(fullPath) {
  if (SENSITIVE_EXCEPTIONS.has(fullPath)) return;
  for (const prefix of SENSITIVE_PREFIXES) {
    if (fullPath === prefix || fullPath.startsWith(prefix + "/")) {
      throw new Error(`已拦截：${fullPath} 属于敏感模块，本连接器不提供访问`);
    }
  }
}

7.5 底线：专用低权限账号

最 有 效 的 一 条 上面三道闸防的是"凭据会不会泄露"，而专用低权限账号限定的是"泄露了损失有多大"。 前者可能被绕过，后者不会 —— 这是唯一无法被绕过的防护。

本案例的做法：不为连接器复用超管账号，而是新建一个绑定 content_ops（内容运营）角色的账号。

角色（预置）角色码能力与边界
超级管理员super_admin全通，包括财务/系统/账号 —— 不该给连接器
内容运营content_ops内容、页面、素材可读可写；上传接口 403（见第十章）
业务运营biz_ops业务侧模块
客服人员service_staff客服相关
一 个 有 利 的 事 实 很多后台的"权限点"只控制前端菜单显隐，不参与 API 鉴权（本案例 SecurityConfig 只用 hasRole，不用 hasAuthority）。 这意味着绑定 content_ops 后，内容/页面/素材接口天然全通，不需要逐条配置权限点 —— 先去源码里确认这一点，能省掉大量配置工作。

八验证与交付：从冒烟到端到端

8.1 三态验证（比"能跑通"更重要）

只测"配置正确时能用"是不够的，配置出错时的表现同样要验证：

状态期望表现为什么这么设计
完全无凭据启动成功，工具数 12，调用时报"未配置 + 怎么修"进程不死，面板不黄点
凭据文件正确启动成功，只读模式 5 个工具，调用返回真实数据正常路径
凭据文件路径错启动成功，调用时报"凭据文件读取失败：…"错误可读，指向明确

8.3 配套 Skill：让 AI 记得住怎么用

光有工具，AI 未必知道什么时候该调。补一个 Skill 把触发场景、硬规则、故障对照固化下来：

~/.workbuddy/skills/miniprogram-content-ops/SKILL.md
---
name: miniprogram-content-ops
description: 通过本地 MCP 连接器读写小程序后台——查内容、查页面 DSL、查素材，
  以及新建/更新/发布/下架。当用户提到「小程序后台」「发布到小程序」
  「改小程序首页」「上架/下架内容」时使用。也覆盖连接器故障排查。
---

## 硬规则（踩过的坑）
- **存草稿 ≠ 发布**。改页面必须 save_page_draft 后再 publish_page。
- **封面用 /uploads/... 相对路径**，不要拼 admin 域名（admin 域 ≠ api 域）。
- **上传 403**：接口挂在 /admin/system/upload，属超管前缀。图片走后台素材库手工传。
- **写操作直打生产库，无二次确认**。发布前先确认目标 ID。

## 常见故障
| 现象 | 处理 |
|---|---|
| code=110101 | 账号密码不符，重跑 setup-credentials.sh |
| 只有 5 个工具 | MP_READ_ONLY=1 |
| 403 | 路径属超管前缀，或账号角色不够 |
为 什 么 单 独 拆 出 SKILL 连接器解决"能不能调"，Skill 解决"该不该调、怎么调"。两者分开的好处是： 换一个后台、换一个连接器，Skill 里的领域规则（草稿≠发布、封面用相对路径）依然可复用。

九扩展与运维

9.1 加一个新工具：两处改动

  1. 在 tools.js 的 TOOLS 数组加一条声明（name / description / inputSchema）
  2. 在 callTool 的 switch 里加一个 case；若是有副作用的，同时登记进 WRITE_TOOLS
自检
node scripts/smoke.js mp_新工具名 '{"参数":"值"}'

9.2 改动落点速查

要做什么动哪个文件
加/改接口src/tools.js —— 声明 + case
放开某个敏感模块src/config.js 的 SENSITIVE_PREFIXES / SENSITIVE_EXCEPTIONS

9.3 版本与回滚

  • 改动原则：只增不改。已交付的行为不变更，新能力走新增工具或新增版本
  • 改代码前先跑一次 node scripts/smoke.js 留基线输出
  • 改 mcp.json 前先备份，配置错误会让连接器整体不可用
  • 生产侧的后台部署另走既有发布流程，连接器改动与后台改动分开记录

十踩坑清单

以下每一条都是本案例中真实发生并修复的，按"现象 → 根因 → 处理"排列。

现象根因处理
面板黄点 /「切换服务器状态失败」 凭据缺失时 process.exit(1)，进程启动即退出，面板状态卡死 配置改软失败：照常启动并列出工具，错误在调用时给出指引
code=110101 用户名或密码错误 read -s 不回显，密码输入易错；也曾误用不存在的用户名 setup 脚本改为写完当场验证登录并回显字符数；失败可原地重输
建账号报 409，还弹两条错误 用户名撞车（HTTP 409）；前端请求层已按后端 message 弹过并置 toastHandled，页面 catch 未识别该标记又弹一次 换用户名；页面 catch 加 if (!e?.toastHandled) 守卫，并补 409 兜底文案
后台看不到「管理员账号」菜单 侧边栏菜单是硬编码数组，与 router 不是一份数据；页面和路由其实都已部署 菜单数组补该项 + roles:['super_admin'] 过滤；临时可直连 URL
mp_upload_file 必 403 上传接口路径 /admin/system/upload 落在 SecurityConfig 的超管前缀下 短期：图片走后台素材库手工传；长期：把上传路径挪到 /admin/assets/upload
页面改了但线上没变 只调了 save_page_draft，没调 publish_page 两步都要做，并在工具 description 与 Skill 里写死这条
改内容后封面/标签消失 后台 PUT 是全量覆盖，只传部分字段会清空其余 工具内部先 GET 再合并后 PUT
两 条 通 用 教 训 ① 时序比代码更容易出错：先改配置、后建凭据，中间那次拉起就会失败，且失败状态会被缓存。
② 看不见的输入要当场验证：read -s 输入的密码、不回显的表单，都应该在写完后立刻用它打一次真实请求，而不是等到下游报错再回头查。
